# P3 — Migration 0036, `exercise_configurations` Constraint Rename Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rename `exercise_configurations`' two constraints onto the `uq_<table>_<column>` convention its mirror table `activity_configurations` already uses, via a new migration.

**Architecture:** One new migration, `0036`, containing two `ALTER TABLE … RENAME CONSTRAINT` statements and their inverses. Metadata-only — no table rewrite, no data touched. `app/src/db/schema.ts` picks the new names up from `drizzle-kit introspect`, never by hand.

**Tech Stack:** PostgreSQL (Neon), dbmate, drizzle-kit.

**Spec:** `docs/superpowers/specs/2026-09-17-technical-debt-sweep-design.md` §5

**Issues closed:** #295

## Global Constraints

- Branch off `main`, named `fix/p3-constraint-naming`. Never commit to `main`. Do not commit unless the user asks.
- **Never modify an applied migration.** `0001`–`0035` are immutable; this is a new numbered migration.
- The database never generates ids; nothing in this migration creates rows.
- Never hand-edit `app/src/db/schema.ts` — it is `drizzle-kit introspect` output.
- Target names, confirmed with the user: `uq_exercise_configurations_exercise_session` and `fk_exercise_configurations_exercise_session`. The column is `exercise_session_id`, so `<column>` is `exercise_session` — the longer form is deliberate.
- Production application happens through the deploy pipeline's migrate job behind its Neon-branch rehearsal (D288). Never apply to production by hand.

### Task 2: Write and apply the migration

**Files:**
- Create: `database/migrations/0036_exercise_configuration_constraint_naming.sql`
- Modify: `app/src/db/schema.ts` (regenerated, not hand-edited)

**Interfaces:**
- Consumes: Task 1's evidence.
- Produces: constraints named `uq_exercise_configurations_exercise_session` and `fk_exercise_configurations_exercise_session`.

- [ ] **Step 1: Write the migration**

Create `database/migrations/0036_exercise_configuration_constraint_naming.sql`, following `0034`'s header style exactly:

```sql
-- ============================================================
-- Migration: 0036_exercise_configuration_constraint_naming.sql
--
-- Purpose:
-- Rename exercise_configurations' two constraints onto the
-- uq_<table>_<column> convention the rest of the chain uses.
--
-- exercise_configurations (0005) named its constraints
-- uq_exercise_configuration_session / fk_exercise_configuration_session:
-- singular table noun, shortened column. Its mirror table one
-- layer up, activity_configurations (0030), uses
-- uq_activity_configurations_activity, as do exercise_types and
-- exercise_ruleset_versions (0027). Two tables that mirror each
-- other column-for-column carried two naming conventions
-- (issue #295).
--
-- RENAME CONSTRAINT is metadata-only: no table rewrite, no row
-- is read or written, and nothing in app/src queries either name
-- (the only reference is drizzle's generated schema.ts, which
-- db:introspect regenerates). Fully reversible.
-- ============================================================

-- migrate:up
ALTER TABLE exercise_configurations
    RENAME CONSTRAINT uq_exercise_configuration_session
    TO uq_exercise_configurations_exercise_session;

ALTER TABLE exercise_configurations
    RENAME CONSTRAINT fk_exercise_configuration_session
    TO fk_exercise_configurations_exercise_session;

-- migrate:down
ALTER TABLE exercise_configurations
    RENAME CONSTRAINT uq_exercise_configurations_exercise_session
    TO uq_exercise_configuration_session;

ALTER TABLE exercise_configurations
    RENAME CONSTRAINT fk_exercise_configurations_exercise_session
    TO fk_exercise_configuration_session;
```

## 0036_exercise_configuration_constraint_naming.sql

Renames `exercise_configurations`' unique and foreign-key constraints from `uq_exercise_configuration_session` / `fk_exercise_configuration_session` to `uq_exercise_configurations_exercise_session` / `fk_exercise_configurations_exercise_session`, matching the `uq_<table>_<column>` convention used by `activity_configurations` (0030), `exercise_types` and `exercise_ruleset_versions` (0027).

Append to `decisions/database.md` with that id + 1:

```markdown
### D<next> — Constraint names are `<prefix>_<table>_<column>`, with the column named in full
Status: Accepted · Date: 2026-09-17
Decision: every constraint is named `uq_`/`fk_`/`chk_` + the table's own (plural) name + the local column with `_id` stripped. Migration 0036 repoints `exercise_configurations`' two constraints onto it; `activity_configurations` (0030), `exercise_types` and `exercise_ruleset_versions` (0027) already follow it. Applied migrations are not edited — the rename is a new migration.
Reason: `exercise_configurations` (0005) used a singular table noun and a shortened column (`uq_exercise_configuration_session`), so the two mirror tables carried two conventions with no functional difference to explain it (issue #295). A reader comparing them side by side had to check which era a table came from. Deriving the name mechanically removes that judgement call: `exercise_session_id` yields `exercise_session`, even though the shorter `_session` reads better, because the shorter form repeats 0005's habit of naming something other than the column.
Consequences: constraint names are longer. Nothing queries them by name today, but `app/src/services/session.service.ts` does branch on `uq_sessions_single_active` when mapping a unique violation to a domain error — so any future rename of a constraint that appears in an error-mapping path must change both in the same commit. `app/src/db/schema.ts` follows automatically through `db:introspect`.
```

# Bob's 27 Easy (BOBS27_V2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Bob's 27 Easy: the same run as Traditional, but the score may go negative and nobody dies, selected by a setup switch, adding no new duplication.

**Architecture:**
- **Registration (Task 1):** a new ruleset version `BOBS27_V2`: `Bobs27V2Config` built by extending the V1 schema, one validator builder shared by both keys, rows in the four capability maps, seat cap, progress summarizer, seed `0050` and the `0007` triples.
- **Engine (Task 2):** one policy choice inside `bobs27Rules` (skip the death check when `mode` is `"EASY"`), a second factory on the same spec and class. The fold, state shapes and outcome logic are unchanged: with no death there is no `LOST`, so the existing score-compare branch already decides 1v1.
- **Setup and play (Task 3):** an `easy` flag on the existing setup controller, a `Switch` on the existing form, resume and play again accepting both keys, a results title for a deathless run.
- **Proof (Task 4):** stats, replay, resume-deck and survival tests; no source change expected.
- **Docs and gates (Task 5):** decision block, inventory, seed lists.

**Tech Stack:** TypeScript, Zod 3.25, Vitest, Astro + Alpine, PostgreSQL seeds, bash gates.

**Spec:** `docs/superpowers/specs/2026-10-23-bobs-27-easy-design.md`. Rules: `docs/game-rules/rulesets/bobs-27.md` (Easy rows `V2`). Model commit for the registration touch points: `6ee4c09` (Around the Clock V3). Model plans: `docs/superpowers/plans/2026-10-22-track-t2-nine-lives.md`.

## Spec refinements (write back into the spec on approval)

1. **No fold or outcome change (§4).** Easy never produces `LOST`, so `foldBobs27State` and `elimination` are untouched; the existing `scoreCompareOutcome(..., "HIGHEST")` branch already decides 1v1. Only `bobs27Rules` changes (the death check). Solo `WON` means "finished the path".
2. **No Mode row in results, no Mode cell in replay (§6).** The results title carries the distinction ("Run complete!"); the score cell already renders negatives. A `Mode` row would be a new `x-if` row set and a new replay cell for a value nobody acts on.
3. **`constants.ts` is not touched (§5, §7).** `HEATMAP_ONLY_LAYOUTS` is keyed by each game's primary card (`primaryCards()`); no V2 key appears in it (Shanghai V2 and Around the Clock V2/V3 are absent too).
4. **The #1061 gap is closed on `main` (§12).** `cardForRuleset` resolves a variant key through `GAME_TYPE_BY_RULESET`; the `BOBS27_V2` row there (Task 1) is what keeps Easy sessions in the resume deck. A test pins it (Task 4).
5. **Validator builder (§5).** `bobs27ValidatorFor(schema)` replaces the inline options; V1 export unchanged in name and behaviour.
6. **Play again and resume read the session's own key (§6)** from `$store.game.rulesetVersionKey`, not a new config-derived helper.

## Review Focus

1. Easy never ends a run early: a visit that would take the score to 0 or below mid-path leaves the seat `IN_PROGRESS`, and `wouldComplete` stays false there (Task 2).
2. A negative score everywhere a score is read: `currentScoreFor`, results snapshot, session-progress `big`, stats `scoreAfter.min` (Tasks 2, 3, 4).
3. 1v1 Easy with equal scores ties; with a negative seat and a positive seat the positive wins; nobody is eliminated (Task 2).
4. V1 sessions replay byte-identical through the shared engine, and V1 snapshots (no `mode`) never read as Easy (Task 2).
5. Easy sessions resume after reload, play again with `mode` resent, and stay in the resume deck (Tasks 3, 4).

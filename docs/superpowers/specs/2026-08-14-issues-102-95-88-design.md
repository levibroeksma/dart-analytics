# Design: Jumpy Interface (#102), Bob's 27 Summary (#95), Finish Modal (#88)

> Three independent, small UI fixes bundled into one branch. Personal-best/high-score
> pill from #95 is explicitly deferred (owner decision) — no PB concept exists
> anywhere in the app yet and would need a new stored comparison value.

---

## #102 — Jumpy interface

**Root cause:** `app/src/stores/settings.store.ts`'s `captureModeKey`/`inputModeKey`
fields render their defaults (`RECREATIONAL`/`QUICK_SCORE`) before the store's async
`load()` resolves. Two consumers bind straight to those fields with no loading gate,
so the real (e.g. analytics) preference visibly flashes in after load completes:

- `app/src/components/forms/AppModeForm.astro` — radiogroup `:class`/`:aria-checked`
  bound directly to `$store.settings.inputModeKey`.
- `app/src/pages/games/index.astro` (via `app/src/lib/game/games-index.data.ts`'s
  `isVisible()`) — game-card visibility bound to `$store.settings.captureModeKey`.

**Fix:** gate both on the store's existing `loading` boolean, mirroring the working
`loadingReconciliation` pattern already in `ReconciliationBlocked.astro` (same
init-time-true, `x-show`/`x-cloak` shape). No change to `settings.store.ts` itself —
`loading` already starts `false` and flips `true` synchronously at the top of `init()`,
before Alpine removes `x-cloak`.

- `AppModeForm.astro`: wrap the existing radiogroup in
  `x-show="!$store.settings.loading"` + `x-cloak`. Add a sibling skeleton block,
  `x-show="$store.settings.loading"` + `x-cloak`, of two pulse-placeholder option
  shapes using existing `surface`/`border` tokens + Tailwind's built-in
  `animate-pulse` utility (no new shared component — only 2 call sites in this task).
- `games/index.astro`: wrap the `GAME_CARDS` list + "none visible" block in the same
  `!$store.settings.loading` gate; add a matching skeleton row of placeholder cards
  shown while `loading`. Existing per-card `x-show`/`x-cloak` (`isVisible(...)`)
  logic is untouched — it's already correct once settings has loaded, the bug is only
  that it renders once too early.

No store, API, or type changes. No schema/decision-ledger impact — a `07-Frontend`
UI pattern already documented ("Skeleton-first hydration", `00-Overview.md`), applied
to two more consumers.

## #95 — Bob's 27 results modal (personal-best deferred)

File: `app/src/components/layout/games/result-modals/Bobs27Results.astro`
Data: `app/src/lib/game/bobs27-play.data.ts` (`computeStats()`, `resultsSnapshot` type)

**Title:**
- `status === 'LOST'` → **"Game over!"** (was "Lost")
- `status === 'WON'` → **"Winner!"** (was "Won")

**New stats** (both derived, no persistence change), added to `computeStats()`'s
return type and `resultsSnapshot`'s inline type in `bobs27-play.data.ts`:

- **Double hit ratio** — `"H/T"` string. `H` = count of darts across all `turns`
  where `dart.hitTargetNumber === dart.intendedTargetNumber && dart.hitZoneKey ===
  dart.intendedZoneKey` (the same on-target equality `doublesPathPreviewSegments`
  in `doubles-path-play.ts` already uses); `T` = total darts thrown across all turns
  (already computed as `darts` today).
- **Highest number reached** — `doublesPathTargetLabel(targetAt(doublesPath(),
  finalState.targetIndex))`, reusing the exact helper `currentTargetLabel()` in the
  same file already calls. Yields `"D16"`-style or `"BULL"`. `finalState` is the
  `engine.state()` already captured in `uploadAndCompleteSession()` before the store
  reset, so `targetIndex` is read at the same point the existing `score`/`status`
  fields are.

**Rendering:** two new `StatRow`s in `Bobs27Results.astro`'s existing `<dl>`, same
shape as the current `Score`/`Darts` rows, labelled "Double hit ratio" and
"Highest number reached".

**Explicitly out of scope:** the "New high score!" personal-best pill. No PB concept
exists in the app (verified — no matching code, API, or view). Deferred per owner
decision; would need a new stored best-score comparison, likely a `v_*` view or API
call per the "statistics come from API / views" rule, not a pure frontend derivation.

## #88 — Finish game modal

File: `app/src/pages/games/501/play/index.astro`, line 55.

One-line prop change: `confirmLabel="Finish match"` → `confirmLabel="Confirm"` on the
existing `ConfirmDialog` usage (the dialog's `title="Finish match?"` heading is
unchanged — only the button text was called out). This is the only confirm-dialog
button in the app with a non-default label; `ConfirmDialog.astro` already defaults
`confirmLabel` to `"Confirm"`, so this brings the 501 match-finish dialog in line with
every other confirm dialog in the app (e.g. Score Training's finish-session confirm,
which already uses the default).

No literal "Finish game" button text exists anywhere in the repo (confirmed via
repo-wide grep) — this is the only plausible match for the issue's wording.

## Testing

- `AppModeForm.astro` / `games/index.astro`: no unit-testable logic added (D101 —
  `.astro` variant/branching logic is untested by convention); manual verification
  via dev server (throttled network / artificial `load()` delay) that the skeleton
  shows before the real radiogroup/card list.
- `bobs27-play.data.ts`: `computeStats()` is a pure function — add/extend
  `app/tests/lib/game/bobs27-play.data.test.ts` (mirroring existing test file
  location) covering the new ratio and highest-number-reached fields for both WON
  and LOST outcomes, including a 0-darts-thrown edge case for the ratio (should not
  divide by zero — render `"0/0"` rather than throw or `NaN`).
- `Bobs27Results.astro`: no separate test file (D101) — covered by the modal
  rendering `resultsSnapshot` fields already exercised by `bobs27-play.data.test.ts`.
- `501/play/index.astro`: prop-only change, no new test needed.

### D195 — Player settings endpoints ship; the client stops owning last-used modes
Status: Accepted · Date: 2026-08-08
Decision: `GET` and `PATCH /api/players/me/settings` ship as a normal protected route pair. `GET` reads `v_player_settings` (migration `0021`) and falls back to `RECREATIONAL` + `QUICK_SCORE` when the player has no row or either stored mode id is NULL; `PATCH` replaces both modes and creates the row lazily on first write, with no backfill. `PATCH` refuses a capture/input pair no ruleset version declares, returning `VALIDATION_FAILED` with the rejected pair in `error.details.reason` — the service asks `capableRulesets()` (`app/src/lib/game/rulesets/capabilities.ts`), the same declaration migration `0020`'s composite foreign key enforces on `exercise_sessions`. The service returns `ServiceResult { ok, code, details }` rather than throwing, matching `session.service.ts`. No new error code is introduced. Settings stay defaults only: read at session start, copied onto the session, never rewriting history.
Reason: D60 deferred these endpoints and left the client persisting last-used modes locally, which was workable while capture/input mode was a per-session choice made on the setup screen. The visual board makes it an account-level app mode that the profile screen sets and the games page filters by, so it must survive a device change and be readable by the server — a `localStorage` value cannot be either. Refusing an uncapable pair at write time is what keeps the setting from stranding a player in a mode where every game card is hidden.
Consequences: `06-Spec/03-Player-Layer.md`'s `player_settings` section moves from "v1 status: deferred" to shipped, and `DECISIONS.md`'s Deferred list loses its `player_settings endpoints` entry. The `players` domain now has a `me` sub-resource; `PATCH /api/players/me` (rename, D76) remains deferred and is unaffected. `PlayerSettingsResponse` omits the view's `player_id` and `updated_at` — the caller is always `me` and no client reads the timestamp — so widening it later is additive. A player whose stored pair stops being capable (a ruleset version dropping a mode) is not migrated: `GET` still returns the stored pair, and only the next `PATCH` is refused.
Supersedes: D60 — only its deferral clause (the client-owns-last-used-modes arrangement recorded against it). D60's own rule stands unchanged: `POST /api/sessions` still requires `captureModeKey` + `inputModeKey` on every request, and settings are only the values the client defaults those fields to.

### D221 — `POST /api/sessions` accepts an ordered `participants[]`
Status: Accepted · Date: 2026-08-21
Decision: The create-session request gains an optional `participants[]` of `{ participantTypeKey: "PLAYER" | "GUEST", displayName?, sideKey }`. Array order IS seat order — it decides who throws first in leg 1. The service mints one participant row per entry in the same transaction as the session, copies the `PLAYER`'s `displayName` from `players.display_name` (ignoring any client-supplied value), and composes the resulting refs into the configuration snapshot's `seats`. Omitting the field reproduces the single-`PLAYER` session exactly. `session-seats.service.ts` is the single place cross-field agreement is asserted, before any write: 1–4 seats, exactly one `PLAYER`, every guest named, one seat per `sideKey`, and more than one seat only for `501_V1`.
Reason: D61 deferred guest participants as an explicitly additive `participants[]`; this delivers exactly that shape. The guards live in the service rather than in the Zod schema because two of them depend on the ruleset being created, which the request schema cannot see, and splitting them across both layers would put the rules in two places.
Consequences: `insertSessionRecords` takes a participant array in place of its four single-participant fields and returns `{ sessionId }` only. Duplicate guest display names are deliberately allowed — seats are identified by ref, not name, and refusing them would reject valid input. The one-seat-per-side guard is what stops 2v2 preparation from silently half-working: `sideKey` and per-side folding exist, the pairing does not. The events batch endpoint is unchanged; a turn's `participantRef` may now simply vary within one batch, which `validateBatchReferences` already allowed.
Supersedes: D61

### D239 — `ROUNDS` batch validation checks the turn-count limit per seat, not per session
Status: Accepted · Date: 2026-08-27
Decision: `duration_type: "ROUNDS"`'s `duration_value` is a per-seat budget — every seat plays out its own full round count before a match is decided (`durationSeatComplete`, `modules/game/seat-state.module.ts`). The shared batch-validation check (`exceedsRoundsLimit`, `quick-score.validator.ts`, used by Score Training and TUOD) now checks each participant's own existing-plus-batch turn count against `duration_value` independently, via a new `ExistingTurnCounts` map (`app/src/repositories/interfaces.ts`) keyed by participant id instead of one session-wide number.
Reason: The old check summed turns across every seat and compared that to the single-seat budget, so any 2-seat ROUNDS session's legitimate combined turn count (up to 2×`duration_value`) tripped the "exceeds limit" rejection — always, at or before the real finish. Solo sessions never hit this (one seat's turns are the whole session's turns), which is why it shipped unnoticed until 1v1 (issue #169).
Consequences: `RulesetValidator.validateBatch`'s `existingTurnCount: number` field is renamed `existingTurnCounts: ExistingTurnCounts` — a breaking signature change for every ruleset validator, though only Score Training's and TUOD's `validateBatch` read the value; the rest carry the field only to satisfy the interface. `countTurnsForSession` (`session.repository.ts`) returns a per-participant map instead of a scalar.

### D258 — `GET /api/statistics/overview` composes 4 views in the service layer, not one dedicated aggregate view
Status: Accepted · Date: 2026-09-06
Decision: The endpoint D63 reserved is implemented reading `v_session_overview`, `v_player_visit_facts`, `v_player_leg_facts`, and `v_double_out_checkout_darts` through `repositories/statistics.repository.ts`, with all aggregation (streaks, score bands, averages, best leg, double accuracy) done in `services/statistics.service.ts` via five pure modules under `modules/stats/`/`modules/game/`, rather than a single `v_statistics_overview` view doing the aggregation in SQL.
Reason: D257's `v_player_visit_facts`/`v_player_leg_facts` were already designed to expose row-level facts, not pre-aggregated numbers — the approximation (best-effort darts-thrown) and exclusion (doubles-excluded scoring average) logic is application judgment a view can't safely encode (`05-Views.md` forbids workflow decisions in views), and duplicating it into a new aggregate view would fork the same logic the pure modules already hold. `00-Overview.md`'s original D63 note suggested "e.g. `v_statistics_overview`" as an example, not a requirement — "view-backed" is satisfied by reading existing views, not by inventing one new view per endpoint.
Consequences: Every response field's correctness depends on the pure modules' own tests, not a SQL assertion — `database/verification/` gains no new script for this endpoint. Win-rate is excluded from the response shape entirely, pending a separate session-replay design. If this composition is ever measured slow, `05-Views.md`'s own performance order applies (query structure, then indexes, then materialization) before reaching for a dedicated aggregate view.
Supersedes: none.

### D271 — Leaving a training routine abandons the activity itself, not just its current step's session
Status: Accepted · Date: 2026-09-13
Decision: `PATCH /api/training-sessions/:activityId/abandon` is a new endpoint, mirroring the existing `PATCH /api/training-sessions/:activityId/complete` — both now delegate to one `transitionTrainingActivity(playerId, activityId, statusKey)` helper (`training-session.service.ts`) that resolves `game_statuses` for either `COMPLETED` or `ABANDONED` and updates `activities.status_id`. `balancedTrainingPlay()`'s new `abandonAndExit()` calls it after abandoning the current step's own `exercise_sessions` row through the existing `PATCH /api/sessions/:sessionId` (`{ status: "ABANDONED" }`) — reusing the `ABANDONED` status `exercise_sessions` already accepts, now also valid for `activities`. `playAbandonAndExit` (`play-lifecycle.ts`) gains an optional `redirectTo` (default `/games`, every existing caller unaffected) and now awaits its `onAbandoned` callback (previously fire-and-forget) so the Finishing step's own wrapped abandon (`finishingStep()`, `finishing-step.data.ts`) can await the activity-abandon call before the store resets and the page redirects to `/training`.
Reason: issue #274 asked for training mode to gain a Leave control like every game mode's; doing that without also closing out the `activities` row would leave it `ACTIVE` forever every time a player left early, since — unlike `exercise_sessions` — nothing enforces a single active `activities` row per player. That is a wrong historical record, not just a missing UI affordance: "store what happened" requires the record to say abandoned when it was.
Consequences: `abandonTraining`/`completeTraining` are now thin wrappers over one shared helper. `06-API/00-Overview.md`'s Route Surface table lists no `/api/training-sessions/*` endpoint at all — that gap predates this change (the whole `start`/`steps`/`complete` family was already undocumented) and is logged in `FINDINGS.md` rather than backfilled here.
Supersedes: none.

### D277 — A dart exercise's step session carries a capture pair and uploads through the same batch route, with no per-ruleset batch validator
Status: Accepted · Date: 2026-09-14
Decision: `startTrainingStep`'s non-game path creates a `SWITCHING`/`DOUBLE_PATTERN` step session under the `ANALYTICS` + `VISUAL_BOARD` capture pair (`WARM_UP` keeps the NULL pair it had), as the playable-Balanced-Training design already specified. `appendBatch` no longer requires a *game* ruleset version on the session: `findSessionRow` now also returns `exercise_ruleset_versions.implementation_key`, and the batch is validated as (a) a game session — game ruleset key present, its `RulesetValidator` required and run, unchanged — or (b) a dart-exercise session — `exerciseRulesetWritesDarts(key)` true for `SWITCHING_V1`/`DOUBLE_PATTERN_V1`, admitted on the structural checks alone. A capture pair remains mandatory for any batch, so a Warm-Up session (no capture pair, writes no dart) still returns `INTERNAL_ERROR`.
Reason: Balanced Training died at "Could not continue to the next step. Try again." the moment the Switching countdown expired, and D276's intended-zone fix did not reach the real cause. `advanceAfterStepCompletion` uploads the step's darts first, and `appendBatch` rejected every dart-exercise batch before any dart was ever examined: the step session is created with `ruleset_version_id`, `capture_mode_id` and `input_mode_id` all NULL (D264's parallel-contract split puts the exercise ruleset in its own column), and the service hard-required all three plus a game `RulesetValidator` — of which `SWITCHING_V1` has none, and cannot: exercise rulesets validate configuration only. Reproduced as a unit test against `appendBatch` before the fix (`session.service.test.ts`), which returned `INTERNAL_ERROR` for exactly that session shape.
Consequences: `SessionRow` gains `exerciseRulesetVersionKey` (one added LEFT JOIN in `findSessionRow`); every mocked session row in the service tests gains the field. Switching and Double Pattern darts now persist, so the step's facts reach `turns`/`darts` and the routine advances to the next step. Server-side rule validation of a dart-exercise batch is a deliberate gap, not an oversight: the exercise engines are the only authority on their own scoring today, and adding `validateBatch` to `ExerciseRulesetValidator` is a separate design. The stale comment on that interface ("a non-game exercise writes no turns and no darts") is corrected in place. The pre-existing test asserting `INTERNAL_ERROR` for "a non-GAME exercise session" is re-pointed at Warm-Up — the same guarantee, now named by the session that actually holds it — rather than deleted.
Supersedes: none.

### D281 — A turn-less batch needs no capture pair, so Warm-Up's `EXERCISE_SECTION` stages upload through the same batch route
Status: Accepted · Date: 2026-09-15
Decision: `validateBatchAgainstRuleset` (`session.service.ts`) now checks whether the batch carries any turn at all (`batch.stages.some((stage) => stage.turns.length > 0)`) before requiring a capture pair. A turn-less batch is admitted on `appendBatch`'s structural checks alone, with no capture-pair check and no ruleset lookup — there is no dart in it to validate. A batch carrying a turn still requires `session.captureModeKey`/`inputModeKey`, unchanged. Client-side, `uploadCurrentStepFacts` (`balanced-training-play.data.ts`) now uploads `this.activeDartEngine() ?? this.warmUpEngine`, so a completed or abandoned Warm-Up step's `WarmUpEngine.facts()` — one `EXERCISE_SECTION` stage per phase entered, `turns: []` — reaches the server the same way Switching's and Double Pattern's dart facts already do.
Reason: issue #309 — Warm-Up's phase-by-phase record was computed in memory (`WarmUpEngine.advance()`) but never uploaded: `uploadCurrentStepFacts` only ever read `activeDartEngine()` (Switching/Double Pattern), so its call was always a no-op for a Warm-Up step, and the session was marked `COMPLETED` with zero persisted stages — contradicting root `CLAUDE.md`'s "store what happened". D277 (2026-09-14) had just re-affirmed that a Warm-Up batch "still returns `INTERNAL_ERROR`", reasoning from "a capture pair remains mandatory for any batch" — true for a batch that writes a dart, but stricter than the actual constraint: a batch with no turn carries nothing a capture pair or ruleset validator could check.
Consequences: Warm-Up's `EXERCISE_SECTION` stages are now real rows in `stages`, one per phase entered, with no owning `turns`. The existing test asserting `INTERNAL_ERROR` for a Warm-Up session (`session.service.test.ts`) keeps passing unchanged — its batch fixture carries a turn, so it still exercises the capture-pair requirement, now correctly scoped to turn-carrying batches only.
Supersedes: D277 (narrows its "a capture pair remains mandatory for any batch" clause to batches that carry a turn).

### D282 — `SessionApiError` carries the envelope's `requestId` and `details`, and the training routine's step-advance error shows the request id
Status: Accepted · Date: 2026-09-15
Decision: `SessionApiError` (`client/api/sessions.ts`) gains two optional constructor fields, `requestId` and `details`, populated from the same `ApiFailure` envelope fields at every throw site in `client/api/sessions.ts` and `client/api/training-sessions.ts`. `balancedTrainingPlay()`'s `completeCurrentStep` (`balanced-training-play.data.ts`) appends the request id to its on-screen message when the caught error carries one: `Could not continue to the next step (${code}, ${requestId}). Try again.`
Reason: issue #332 — Balanced Training broke advancing out of a Double Pattern ("Doubles") step into the Finishing (TUOD) step with `Could not continue to the next step (INTERNAL_ERROR). Try again.` Investigation (client and server code for `advanceAfterStepCompletion`, `uploadCurrentStepFacts`, `appendBatch`/`validateBatchAgainstRuleset`, `startTrainingStep`/`startGameStep`, the `uq_sessions_single_active` conflict path, and the Neon serverless driver's own error shape) found no reproducible defect in the code exercised by this session's environment, and a client-only reproduction of the same step transition passed. `middleware.ts`'s `onRequest` already logs an uncaught server error's full detail — `console.error([api] uncaught error requestId=..., error)` — but never returns it to the client (`INTERNAL_ERROR`'s registry message is the fixed string "Internal error" for every cause, D-frozen in `errors.ts`), and `SessionApiError` was additionally dropping the one thing the envelope does return safely, `requestId`, before it ever reached the UI. Without it, a generically-classified `INTERNAL_ERROR` on screen cannot be correlated to the matching Worker log line that names the real cause. This is instrumentation to close that gap for the next occurrence, not a fix to a located defect — the underlying trigger for issue #332 is still open pending a Worker-log look at the real `requestId`.
Consequences: Every `SessionApiError` thrown by the two session API clients now carries `requestId`/`details` when the server supplied them; nothing currently reads `details` besides the two new unit tests. The training routine's `error` string gains a trailing request id when present, harmless to the one exact-string test that predates a `requestId` on its fixture error (still empty, so the format is unchanged for that case). `sessions.test.ts` and `training-sessions.test.ts` each gain a case asserting the envelope's `requestId`/`details` land on the thrown error; `balanced-training-play.data.test.ts` gains a case asserting the on-screen message includes it.
Supersedes: none.

### D283 — A training activity is read player-scoped, and its terminal transition is guarded inside the UPDATE
Status: Accepted · Date: 2026-09-16
Decision: `findActivityConfiguration` (`training-session.repository.ts`) takes `playerId` and inner-joins `activities`, so an activity the caller does not own reads as `undefined`; `startTrainingStep` maps that to `SESSION_OWNERSHIP_MISMATCH` (403) before any `exercise_sessions` row is written, making an unknown and a foreign `activityId` deliberately indistinguishable to the caller. `updateActivityStatusRecord` takes `expectedStatusId` and carries `activities.status_id = <ACTIVE>` in its own WHERE, so the "still active" check *is* the UPDATE rather than a read preceding it; `transitionTrainingActivity` resolves the `ACTIVE` id alongside the target status, and on a zero-row update re-reads the activity player-scoped (new `findActivityStatus`) only to classify the failure — `NOT_FOUND` when no such activity exists for this player, `SESSION_ALREADY_COMPLETED` (409) when one does.
Reason: issues #336 and #335. The step-start path filtered only on `activity_id`, so any authenticated player could read another player's configuration snapshot and insert sessions into their activity — against `06-API/02-Middleware-And-Layering.md` Rules #5, "all protected queries must be player-scoped". The transition path rewrote `status_id` and `completed_at` with no status check at all, so `complete` followed by `abandon` destroyed a completed routine's original `completed_at` — against root `CLAUDE.md`'s first hard invariant. `session.service.ts`'s `updateSessionStatus` already guarded the same way for game sessions (read, compare to `ACTIVE`, return `SESSION_ALREADY_COMPLETED`); the training path is the copy that lost the check. The guard is put in the UPDATE predicate rather than copied as a read-then-write because two concurrent transitions on one activity would both pass a prior read and the second would still overwrite the first's timestamp.
Consequences: `findActivityConfiguration` and `updateActivityStatusRecord` change signature; both callers are in `training-session.service.ts`. An unknown `activityId` on step-start now answers 403 instead of the previous 422 `VALIDATION_FAILED` ("unknown sequenceNumber") it fell through to. `complete`/`abandon` keep answering `NOT_FOUND` for an activity that is not the caller's — their UPDATE was already player-scoped, and that asymmetry with step-start's 403 is left as-is rather than widened in a bugfix. Client-side `abandonTraining` after a routine already completed now throws on a 409 instead of silently rewriting history; no shipped UI path does that, since the summary modal, not the Leave control, follows completion. No schema backstop was added: tying `exercise_sessions.player_id` to its activity's owner is a composite-FK change to an applied migration's table and belongs to its own task, not to this fix.
Supersedes: none.

### D285 — `isActiveSessionConflict` walks the `cause` chain, and the routine names an already-active Finishing game
Status: Accepted · Date: 2026-09-16
Decision: `isActiveSessionConflict` (`session.service.ts`) follows the error's `cause` chain (bounded to 8 links, self-reference guarded) instead of reading `code`/`constraint`/`message` off the top-level error only. The routine's step-advance message moves out of `balancedTrainingPlay()`'s `completeCurrentStep` into `stepAdvanceErrorMessage` (`lib/training/step-advance-error.ts`), which maps a `SESSION_ALREADY_ACTIVE` failure to its own message — "You have an unfinished Ten Up One Down game. Finish or abandon it under Games, then start this routine again." — and every other coded failure to the existing code+requestId string.
Reason: issue #355, the located cause of #332's symptom. Production row state for the failing run (activity `01a0aad3`, 2026-09-16) shows the Double Pattern step session completed with 1 stage / 9 turns / 27 darts persisted and `completed_at` set, and no step-4 session row created at all: `appendBatch` and `completeSession` both succeeded, and the failure was `startTrainingStep` for the GAME step.

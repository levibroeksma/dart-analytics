### D195 — Player settings endpoints ship; the client stops owning last-used modes
Status: Accepted · Date: 2026-08-08
Decision: `GET` and `PATCH /api/players/me/settings` ship as a normal protected route pair. `GET` reads `v_player_settings` (migration `0021`) and falls back to `RECREATIONAL` + `QUICK_SCORE` when the player has no row or either stored mode id is NULL; `PATCH` replaces both modes and creates the row lazily on first write, with no backfill. `PATCH` refuses a capture/input pair no ruleset version declares, returning `VALIDATION_FAILED` with the rejected pair in `error.details.reason` — the service asks `capableRulesets()` (`app/src/lib/game/rulesets/capabilities.ts`), the same declaration migration `0020`'s composite foreign key enforces on `exercise_sessions`. The service returns `ServiceResult { ok, code, details }` rather than throwing, matching `session.service.ts`. No new error code is introduced. Settings stay defaults only: read at session start, copied onto the session, never rewriting history.
Reason: D60 deferred these endpoints and left the client persisting last-used modes locally, which was workable while capture/input mode was a per-session choice made on the setup screen. The visual board makes it an account-level app mode that the profile screen sets and the games page filters by, so it must survive a device change and be readable by the server — a `localStorage` value cannot be either. Refusing an uncapable pair at write time is what keeps the setting from stranding a player in a mode where every game card is hidden.
Consequences: `06-Spec/03-Player-Layer.md`'s `player_settings` section moves from "v1 status: deferred" to shipped, and `DECISIONS.md`'s Deferred list loses its `player_settings endpoints` entry. The `players` domain now has a `me` sub-resource; `PATCH /api/players/me` (rename, D76) remains deferred and is unaffected. `PlayerSettingsResponse` omits the view's `player_id` and `updated_at` — the caller is always `me` and no client reads the timestamp — so widening it later is additive. A player whose stored pair stops being capable (a ruleset version dropping a mode) is not migrated: `GET` still returns the stored pair, and only the next `PATCH` is refused.
Supersedes: D60 — only its deferral clause (the client-owns-last-used-modes arrangement recorded against it). D60's own rule stands unchanged: `POST /api/sessions` still requires `captureModeKey` + `inputModeKey` on every request, and settings are only the values the client defaults those fields to.

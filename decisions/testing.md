### D224 — A source edit with no test edit is not a completed task
Status: Accepted · Date: 2026-08-21
Decision: `scripts/check-test-coverage.sh` (with `scripts/check_test_coverage.py`) fails any change set that modifies a runtime `.ts` file under `app/src/` or `app/scripts/` unless a test importing that file changed in the same set. It runs as the fourteenth `.husky/pre-commit` gate and as an eighteenth `quality.yml` structure gate, where the `structure` job now checks out with `fetch-depth: 0` so the merge base exists. Coverage is decided by resolving each test's import specifiers through `app/tsconfig.json`'s alias table, not by filename, because `app/src/lib/utils/is-nav-active.ts` is covered off-mirror by `app/tests/utils/is-nav-active.test.ts`. Three exemptions are derived, never listed by name: `.d.ts` files; modules that declare no runtime value of their own, which covers every pure re-export barrel; and edits whose runtime shape is unchanged once type declarations are stripped, so adding a type to a file that also holds Zod schemas costs nothing. `drizzle-kit introspect` output is the one path-keyed exemption, with the owning command recorded beside it. No per-file silencer exists.
Reason: the suite going green proved only that the assertions that already existed still held. Nothing in the repository asked whether any assertion described the change under review, and the completion bar — `validate:app` — could be satisfied by a diff that moved behaviour and touched no test at all. Writing this gate immediately found one: `ParticipantInput`, the Zod schema deciding which participant payloads `POST /api/sessions` accepts, shipped with no test parsing it; `app/tests/pages/api/sessions/types.test.ts` was written in the same pass. A silencer was considered and rejected — an escape hatch would be reached for on exactly the changes the gate exists to catch, and the honest cost of a change that needs no new assertion is opening the covering test to confirm the existing ones still describe the behaviour.
Consequences: every task that edits runtime code now edits a test, and a file with no covering test cannot be changed until one is written — which converts the untested corners of `app/src/` (the Alpine registration modules, `lib/server/envelope.ts`, `stores/board-input.store.ts`) from invisible debt into a bill payable on first touch. That is deliberate and it will slow some tasks down. The gate proves a covering test file was edited, never that the edit asserts anything: a whitespace change satisfies it, and it cannot catch a test repointed at a different input to keep it passing — root `CLAUDE.md`'s test invariant and human review still carry that. Type-shape comparison strips declarations by consuming each from its keyword to its own terminator rather than by splitting the file into statements, because a conditional type returns to depth zero twice before it ends and statement splitting left the tail behind as apparent runtime code. It fails closed: a file with no previous version, and any change it cannot compare, counts as changed.

### D294 — A verification script that transcribes a code constant is gated by the same parity test as the seed
Status: Accepted · Date: 2026-09-17
Decision: `app/tests/lib/game/rulesets/capability-seed-parity.test.ts` now asserts `database/verification/0007_capability_seed_checks.sql` against `RULESET_CAPABILITIES` as well as the seed. Its two `VALUES` lists (Step 2's per-triple resolution, Step 4's nothing-else-in-the-table parity) are parsed as separate lists and compared independently, and the triple count the script hardcodes in its Step 1 and Step 2 assertions is derived from the constant rather than read. The generalisation is the rule, not the file: any `database/verification/**` script that restates a TypeScript constant is gated by the test that already owns that constant.
Reason: the constant had three transcriptions, and only two of them were gated. The seed and `capabilities.ts` were held together by this test; the verification script was held together by nothing, and drifted six triples behind across three ruleset versions (`SINGLES_V2` D247, `SHANGHAI_V2` D245, `SINGLES_V3`) without a single gate objecting — issue #304, filed when the drift was noticed by hand. It was invisible because no `DATABASE_URL` reaches the authoring container (D193), so the script that would have reported the mismatch is the one thing nobody runs. A script only executed in an environment the author cannot reach needs its correctness proved somewhere the author can: statically, in the suite. Parsing the two lists separately rather than as one set is deliberate — a combined parse passes whenever either list is current, which is exactly the state #304 was in.
Consequences: adding a ruleset version now fails `npm test` until the verification script is updated alongside the seed and the constant, which is one more file per ruleset and is the point. The test parses SQL with regexes and is coupled to the script's present shape: the `VALUES … ) AS declared` framing, and four assertion strings matched literally. Reformatting the script breaks the test rather than silently passing, which is the right failure direction but is a real maintenance cost, and a third `VALUES` list added to the script would fail the two-list assertion until the test is taught about it. The gate proves the script's text agrees with the constant; it still proves nothing about whether the script passes against a live database — `npm run db:verify` remains unrunnable here and currently fails for reasons tracked in #383 and #384.

### D303 — A repository's write paths are asserted as rendered SQL, not as a mocked builder
Status: Accepted · Date: 2026-09-17
Decision: every mutating repository function, plus the single-active session lookups, has a test that runs the real drizzle builder through `drizzle-orm/pg-proxy` and asserts the statement it emits, via the shared `app/tests/repositories/render-sql.ts` helper. The existing mocked-builder tests stay: they assert the function's control flow and return shape, which rendering does not cover. Functions that open their own transaction (`upsertSettings`, `insertBatchRecords`) get the rendering client through a `vi.mock("@db/client")` of `withTransaction`, in their own test files, because that mock is module-scoped.
Reason: the repository tests mocked the query builder itself, so no test in the suite had ever seen a statement drizzle emits. `abandonActiveTrainingActivities` shipped a predicate built with `exists()` over a raw `sql` chunk, which renders as `exists select 1 ...` without the parentheses Postgres requires; 3996 tests passed and every routine start in production failed 42601 until it was found by hand (issue #397, fixed in #400). Mocking the builder means the only thing under test is the arguments handed to a fake — the translation step where this class of defect lives is skipped entirely. pg-proxy renders without a connection, so the assertion stays a unit test and the "no real Neon calls" rule (D99, D104) holds.
Consequences: the expected statements are written out in full, so any change to a table's columns, a predicate, or drizzle's own SQL generation fails these tests and must be re-read and re-approved. That is the intended cost — an emitted-SQL change is exactly what should not pass silently — but it is a real maintenance tax on schema work, and drizzle version bumps will land in this file. Coverage is deliberately bounded to writes and the single-active reads rather than every read path: those are where a malformed statement loses or corrupts data rather than failing a screen. The tests prove the SQL is well-formed and shaped as intended; they still prove nothing about whether it is correct against the live schema — that remains `npm run db:verify` and the rehearsal job.

### D304 — A store the routine wraps is tested through the real store, never only through a double
Status: Accepted · Date: 2026-09-17
Decision: `app/tests/lib/training/finishing-step-seam.test.ts` drives the Finishing step over a real `tuodPlay()` — real engine, real `recordDart`/`wouldComplete`/`confirmFinish`, only `@client/api/sessions` and `SegmentTimer` mocked — and asserts the whole path a player takes to complete the step, including that the finish confirm is raised without advancing, that confirming advances exactly once, that a failed upload holds the routine in place, and that `resultsSnapshot` is populated for the summary to read. The existing `finishing-step.data.test.ts` keeps its `vi.mock` of `tuodPlay`: it pins the wrapper's own contract cheaply and independently of TUOD's rules. The rule generalises past this file — wherever one store wraps another and overrides part of its behaviour, the seam between them is covered against the real inner store, not only against a double.
Reason: every Finishing-step defect so far (#216, #357, #370) has lived in that seam, and the suite could not distinguish "the routine advances" from "the routine can be reached at all". The one test file that owned the step replaced `tuodPlay` with a hand-written object whose `uploadAndCompleteSession` just set `completionStatus`, so the sequence that actually hangs — the store raising `showFinishConfirm` and waiting for a dialog — executed nowhere. A double asserts the arguments the wrapper passes; it cannot assert that the inner store ever reaches the wrapper's override. Deleting the gate's `return` in `tuod-play.data.ts` fails three of the five new cases and none of the old ones, which is the gap stated as a measurement.
Consequences: the seam test carries a `$store` stub of the same shape `tuod-play.data.test.ts` maintains, so a change to the game store's fields now lands in two fixtures rather than one. That duplication is accepted over extracting a shared fixture, because the two files deliberately stub different sessions — the standalone game's and the routine's timer-expired MINUTES step — and a shared builder would hide which fields each case depends on. The test is bounded to the Finishing step: the Switching and Doubles steps drive engines directly rather than wrapping a play store, so they have no equivalent seam. It proves the store reaches the routine's advance; it proves nothing about the page markup that renders the dialogs, which `app/tests/pages/training/finishing-step-gates.test.ts` owns.

### D200 — A live session's mode pair is read from the session, never from settings
Status: Accepted · Date: 2026-08-09
Decision: The active session's `captureModeKey`/`inputModeKey` are persisted on `game.store.ts` — written from the resolved pair when a session is created and adopted from the server's `activeSession` on every reconcile — and every play-time consumer reads them from there: which shape the engine is built for, and whether the board renders. `$store.settings` is the authority for exactly one thing: the pair a NEW session is created with, via `resolveSessionModePair`.
Reason: App mode is changeable from the settings screen at any time, including mid-match, and `AppModeForm` has no active-session guard. Gating the board on the settings store therefore renders the board over a RECREATIONAL + QUICK_SCORE session; the darts it captures are refused by `validateQuickScoreTurns` for the entire batch at completion, and a batch is all-or-nothing, so the whole session is lost. The settings store answers "how does this player like to score", which is not the same question as "how is this session being scored".
Consequences: This was the fourth appearance of the same defect on one branch — setup pages hardcoding the pair, `playAgain()` rebuilding an engine with the factory default in 501 and again in Score Training, and this. Each was fixed where it was found; the recurrence is what made a single authority necessary rather than a fourth local fix. Reads tolerate `null` (a store predating this field, or a session whose mode has not been fetched yet) by resolving to `QUICK_SCORE`, the engine's own default, and reconcile overwrites it from the server on the next init.

### D208 — Partial dedup of the Doubles Training frontend's mirrored duplication; the rest stays accepted debt, per D182's own revisit clause
Status: Accepted · Date: 2026-08-13
Decision: `DOUBLES_TRAINING_V1`'s frontend was built by mirroring Bob's 27's play-data module and recreational-input component, per its implementation plan — the same pattern D182 already accepted for 501/Score Training. A final whole-branch review flagged the resulting duplication; the owner chose to dedup the specific pieces that encode a real invariant (the BULL/DOUBLE hit-zone mapping, the doubles-path target-label/visit-preview derivation, and the byte-identical input component) into a new shared module (`lib/game/doubles-path-play.ts`) and component (`DoublesPathRecreationalInput.astro`), used by Bob's 27 and Doubles Training. The broader lifecycle duplication (`init`/`retryReconciliation`/`commitDart`/`undoVisit`/`uploadAndCompleteSession`/`back`/`abandonAndExit`/`playAgain`) that Doubles Training also shares with Singles Training — not just Bob's 27 — was explicitly left out of that dedup's scope.
Reason: `doubles-training-play.data.ts` is exactly the "third RECREATIONAL/QUICK_SCORE-shaped game" D182's rationale named as the revisit trigger (Bob's 27, Singles Training, now Doubles Training all share this lifecycle shape). `fallow` confirms the shape: comparing this branch against its base commit, the pre-existing `bobs27-play.data.ts`+`singles-training-play.data.ts` clone family (4 groups) is joined by `doubles-training-play.data.ts` without changing its group count, and a new `doubles-training-play.data.ts`+`singles-training-play.data.ts` family appears (4 groups, 117 lines) — the exact lifecycle overlap left out of scope above. Total `fallow` dupe count moves from 38 clone groups (base) to 42 (this branch); `fallow`'s dead-code count (2 issues) is unchanged, pre-existing on both. Three same-shaped samples are still a narrow basis for choosing a generic lifecycle abstraction that would need to serve Bob's 27's extra `VISUAL_BOARD`/`hiddenTimer` branch too, so full unification is deferred rather than forced into this branch's diff.
Consequences: `fallow`'s dupes gate stays red on this branch, as it already was on `main` before it — not a new regression, and not blocking per `validate-app`'s DB-independent-gates-still-checked, engine/schema-unaffected completion bar. The next ruleset that shares this lifecycle shape (a fourth sample) is the trigger to actually design the shared abstraction, covering all of Bob's 27, Singles Training, and Doubles Training at once rather than pairwise.

### D209 — Doubles/Singles Training's lifecycle overlap deduped ahead of D208's own trigger, once it became a CI gate rather than an observation
Status: Accepted · Date: 2026-08-13
Supersedes: D208 (only the "deferred, wait for a fourth sample" scope decision — D208's account of what happened and why is left intact as history)
Decision: The `init`/`retryReconciliation`/`commitDart`/`undoVisit`/`uploadAndCompleteSession`/`back`/`abandonAndExit`/`playAgain` overlap between `doubles-training-play.data.ts` and `singles-training-play.data.ts` — the exact piece D208 deferred — is now extracted into `lib/game/play-lifecycle.ts`: eight functions generic over `<TConfig, TEngine extends GameEngine<DartObservation, unknown>, TResults>` (the new `PlayLifecycleContext<TConfig, TEngine, TResults>` type in `lib/game/types.ts`, per the type-raising convention), taking an explicit `context` parameter rather than a `this` parameter to sidestep TypeScript's weak generic inference through `.call()`. Each ruleset's own file keeps only what's genuinely specific: its `resumeEngine` callback, its `resultsSnapshot`-building callback, and its `instanceof` engine-narrowing callback. Bob's 27 (`VISUAL_BOARD`/`hiddenTimer` branch) and 501/Score Training (`ScoreInputBuffer` shape) stay out, unchanged from D208.
Reason: D208 treated the 42-clone-group `fallow` count as accepted debt because it matched `main`'s own pre-existing baseline shape (mirrored-ruleset duplication tolerated since D182). What D208 didn't have yet was the discovery, made once a PR was opened against this branch, that `.github/workflows/quality.yml`'s "Stale-usage gate" runs `npx fallow` as a hard pass/fail CI check — and that the branch's duplication percentage (13.2%) had crossed whatever threshold gates that exit code, up from `main`'s own 11.4% (confirmed via a clean clone of `main` at the same commit). That reclassified the deferred overlap from "debt owed to a future cleanup" to "the specific thing failing CI on this PR." The owner chose to pay it down now rather than merge a permanently-red required check.
Consequences: Duplication is back to 10.9%, under `main`'s own 11.4% baseline — `npx fallow` now exits 0. `play-lifecycle.ts` is registered in the File Inventory below. The still-open question is whether Bob's 27 belongs in this same abstraction eventually (D208's original four-way framing) — nothing here forecloses that, but nothing forces it either; the module is written generically enough that folding Bob's 27 in later means adding its `hiddenTimer` branch as another parameter, not a rewrite.

### D211 — Generalize play-lifecycle.ts for VISUAL_BOARD input
Status: Accepted · Date: 2026-08-15
Decision: `play-lifecycle.ts` (`playCommitDart`, `playUndoVisit`, `runPlayAgain`) now optionally supports board input — an additive `hiddenTimer` field on `PlayLifecycleContext` and a mode-gated reveal-then-clear branch, plus a new shared `playVisitMarkers` helper — rather than re-forking Singles/Doubles Training into bespoke play-data modules the way Bob's 27 did.
Reason: D209 excluded Bob's 27 from `play-lifecycle.ts` specifically because `VISUAL_BOARD` needed the board-tap DOM bridge and the 1.5s reveal-then-clear timer the shared module didn't have. With Singles Training and Doubles Training now needing exactly that shape too, re-forking a second and third time would reintroduce the class of duplication D208/D209 paid down. Generalizing is additive and safe: every existing `play-lifecycle.ts` consumer's `inputModeKey` is never `VISUAL_BOARD`, so the new branch is dead code on their path.
Consequences: Bob's 27 itself is unchanged — its own `commitDart`/`undoVisit`/`visitMarkers` stay bespoke, not a forced migration onto the now-generalized shared module. A fourth ruleset needing board input reuses `play-lifecycle.ts` directly with no further architectural change.
Supersedes: D209

### D215 — One shape per game, extracted where measurement found a clone and written down where it did not
Status: Accepted · Date: 2026-08-19
Decision: Two behaviour-preserving extractions plus one exemplar doc and one gate. `lib/game/setup-controller.ts` (`createPresetSetupController`) absorbs the preset setup skeleton six games repeated verbatim — Bob's 27, Shanghai, 121, Around the Clock, Singles Training, Doubles Training — parameterised by four facts (`gameTypeKey`, `rulesetVersionKey`, `playHref`, `label`) and one optional seam (`configOverrides`, used only by the two training games for `order_mode`/`target_order`). `services/rulesets/three-dart.validator.ts` (`createThreeDartValidator`) absorbs the shared assertions five three-dart validators repeated, parameterised by `label`, `configSchema` and a required `dartlessIssue`. `docs/architecture/07-Frontend/09-Adding-A-Game.md` states the 26-file fan-out, names `bobs27` the reference exemplar, and records the route-slug/code-slug split as forced rather than sloppy. `scripts/check-game-wiring.sh` (gate 13 pre-commit, 17 in CI `structure`) holds the six shared registries against each other. `501` and Score Training keep hand-written setup controllers, and `<game>-play.data.ts` is left entirely alone.
Reason: D182 accepted mirrored duplication with two samples and named "a third same-shaped game" as the revisit trigger; D208 and D209 paid down the play-data half of that debt once CI made it a hard failure. The setup half was never revisited, and by the ninth ruleset it had reached six byte-identical files: 961 lines of setup controller and 749 of validator carrying roughly 160 lines of game-specific fact between them. The measurable cost is not the line count but the silence — `bobs27.validator.ts` and `shanghai.validator.ts` differ in 37 lines, of which the only structural difference is that `DEFAULT_MAX_TURN_SCORE` sits at line 19 in one and line 96 in the other, and each validator's doc comment cites a *different* sibling as the file it mirrors. A change to shared behaviour was five or six edits, and an agent making four of them introduced a divergence no test could catch, because each game's suite only ever exercises that game. `play.data.ts` was measured too and deliberately excluded: 189 to 643 lines with no pair closer than 461 differing lines is real per-game rules logic, and extracting from it would invent a shape rather than record one.
Consequences: The 819 existing tests passed unmodified through both extractions, which is the proof that they were behaviour-preserving — a test edited to accommodate an extraction would have been a behaviour change in disguise. Three details of the design spec did not survive the compiler and the plan corrected them: the generic self-typed `PresetSetupContext<Self>` is rejected as a circular type alias (TS2456) so the base type is non-generic and the self-type parameter lives on the factory instead; `overrides` belongs to `createSession`'s `config`, not to `startSessionInput`; and `dartlessIssue` had to become a third required field because the five validators ship three distinct message bodies, two of which a default would have silently reworded. The gate derives both slugs rather than carrying a table — code slug from the validator's directory, route slug from the `href` `games-visibility.ts` already declares — so a ninth game needs no gate edit. What it still cannot prove is that anyone read the exemplar; that boundary is stated in the script's own header.

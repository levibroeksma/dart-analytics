### D205 — The dartboard uses real dartboard colours, not the sky-blue theme
Status: Accepted · Date: 2026-08-10
Decision: `--dartboard-single-dark`/`--dartboard-single-light`/`--dartboard-wire-red`/`--dartboard-wire-green` in `global.css` are recoloured to a real dartboard's black/cream single beds and red/green multiplier rings (`--dartboard-single-dark: oklch(16% 0 0)`, `--dartboard-single-light: oklch(90% 0.045 90)`, `--dartboard-wire-red: oklch(50% 0.19 25)`, `--dartboard-wire-green: oklch(46% 0.14 150)`), replacing values that resolved to the app's sky-blue accent and a near-transparent white. `.dartboard-group .segment text` now reads `var(--dartboard-label)` instead of `var(--accent)`, fixing a pre-existing mismatch where the already-defined white label token went unused and numbers rendered accent-blue. No class or token *name* changed — `DartBoard.astro`'s `.segment.dark`/`.segment.light`/`.bullSegment .single`/`.bullSegment .double` rules already mapped dark beds to the red-named token and light beds to the green-named token, matching a real board's per-wedge convention; only the colour values were wrong.
Reason: Owner direction after using the shipped board — the sky theme reads as an app skin, not a dartboard, on the one surface meant to look like the real object being scored against.
Consequences: `--accent`, `--error`, `--success` and the rest of the app's sky/glass theme are untouched — this is scoped to the four `--dartboard-*` tokens plus the label-fill fix. Verified by rendering the compiled component in a headless browser (its own `:root`/`@theme inline` tokens and `.dartboard-group` rules, not a hand-approximation) and reading each zone's computed `fill` back: dark beds/bullseye resolve to the red hue, light beds/outer bull to the green hue, both single beds to the intended near-black/cream, and label text to white.

### D218 — Undo always renders as the icon, never a text label
Status: Accepted · Date: 2026-08-20
Decision: Every undo control in the app is an icon-only `UndoIcon` with an `aria-label` naming what it undoes. A play screen that wants undo takes it from the input component that already carries it — `ScoreInput.astro`, `BoardInputPanel.astro`, `SinglesRecreationalInput.astro`, `DoublesPathRecreationalInput.astro` — rather than placing a titled `Button` beside it. Recorded in `07-Style-Guide.md` §Buttons and on the Frontend Agent Guide's pre-completion checklist.
Reason: Four of the five undo controls were already icon-only; TUOD's play screen had shipped a full-width `Button title="Undo"` under its action row, which read as a different control doing a different thing. The convention existed in the code and nowhere in the guidance, so nothing caught the fifth one.
Consequences: TUOD's text undo is gone with the keypad that replaced its binary buttons (D217), so no screen presently violates the rule. The rule is prose, not a gate — `scripts/check-astro-conventions.sh` has no notion of which component an icon belongs in — so it holds only as far as the checklist is read.

### D226 — Ban the Tailwind important modifier entirely, both forms
Status: Accepted · Date: 2026-08-21
Decision: `scripts/check-style-tokens.sh` now bans the Tailwind important modifier in both forms — prefix (`!utility`, already banned by D175) and suffix (`utility!`, D175's own sanctioned v4 form). Overrides are composed as plain classes through `cn()`'s merge ordering (`classNameProp` is always merged last in every component's `cn()` call, so a plain conflicting utility already wins); when a primitive's own defaults are too far from what a screen needs, the primitive's variant/prop surface is extended instead (e.g. `Button.astro`'s new `dashed` variant), rather than layering an override on top of it.
Reason: Auditing every `!`-suffixed class in the repo (`GameCard.astro`, `SetupShell.astro`, `FiveOhOneSetupForm.astro`, `ScoreTrainingSetupForm.astro`, `pages/games/index.astro`, `AddGuestButton.astro`, `GuestSection.astro`) found every single usage was a same-category Tailwind utility conflict (`rounded-md` vs `rounded-full`, `bg-white` vs `bg-accent`, `flex-col` vs `flex-row`, …) that `cn()`'s `twMerge` already resolves by class order — confirmed by reading `global.css`'s `.btn`/`.btn-*` rules, which set only transitions/shadows/hover backgrounds, never padding/radius/border-color. The `!` modifier was never structurally necessary anywhere it was used.
Consequences: All 7 files migrated to plain classes in the same change. `scripts/check-style-tokens.sh`'s `IMPORTANT_MODIFIER` check now flags both forms; `07-Frontend/07-Style-Guide.md` and `app/CLAUDE.md`'s Style non-negotiables no longer present suffix-`!` as the correct v4 form.
Supersedes: D175

### D228 — Don't nest `glass` (backdrop-filter blur) elements
Status: Accepted · Date: 2026-08-22
Decision: `SplitScoreboard.astro`'s outer grid drops its own `glass` class. It previously wrapped `SplitScoreboardHalf.astro` → `SinglePlayerDisplay.astro`, whose own card already carries `glass` — two nested `backdrop-filter: blur()` layers, one blurring the other's backdrop.
Reason: reported as the seat name overlapping the score number on a real iPhone 12 Pro in production, not reproducible in this environment's Chromium-only Playwright at matching dimensions (390px width, heights from 844 down to 600) with realistic content, nor in the reporter's own desktop-simulated mobile viewport — pointing away from a layout/sizing bug (which chromium's box model would have shown identically) and toward a WebKit-specific rendering issue. Nested `backdrop-filter` is a documented WebKit compositing/stacking bug category, and grepping every other `glass` usage in the codebase (`ScoreInput.astro`, `Modal.astro`, `BoardInputPanel.astro`, `GameCard.astro`, every `result-modals/*.astro`) found none nested inside another `glass` ancestor — this was the one accidental exception, most likely introduced by copying the single-player container's own glass card styling onto the split scoreboard's outer shell without noticing the card underneath already supplies it.
Consequences: the seat cards already provide the visible glass/blur surface, so removing the outer layer is visually unchanged (confirmed in Chromium; not confirmed against real WebKit in this sandboxed environment — flagged to the user for on-device re-verification, PR #158). Not elevated to a mechanically-enforced rule (no check script) since only this one nested occurrence existed; a future `glass`-on-`glass` addition is caught by review, not tooling. F15 (`FINDINGS.md`) tracks a related, unresolved sizing-pattern audit noticed during this investigation but out of this fix's scope.

### D262 — `SinglePlayerDisplay`'s big number gets an opt-in `fluid` mode using Tailwind v4 container queries
Status: Accepted · Date: 2026-09-09
Decision: `SinglePlayerDisplay.astro` gains a `fluid?: boolean` prop (default `false`, no change to any existing caller). When true, its card div adds `@container` and the big-number `<h1>` swaps the fixed `size`-step class (`text-4xl`/`text-7xl`) for `whitespace-nowrap text-[clamp(1.75rem,13cqw,3rem)]` — a font size expressed as a clamped fraction of the card's own inline width via the native `cqw` unit, rather than a fixed `rem` breakpoint. Quick Subtract (`QuickSubtract.astro`) passes `fluid` on its running-state `SinglePlayerDisplay`, whose score is an arithmetic expression (`"209 - 27"`, up to `"501 - 60"`) instead of a short fixed-width number.
Reason: at the default `text-7xl` step the trivia expression wrapped onto two lines on a phone-width card (reported with a screenshot: `209 - 27` split across two lines). The other 11 `SinglePlayerDisplay` consumers all display short numeric scores (≤3 digits) that already fit `text-7xl`/`text-4xl` on one line, so changing the shared default would have re-sized every existing game's score for no reason and risked a regression nobody asked for. An opt-in prop keeps the fix scoped to the one caller whose content length actually varies, while still reusing the shared component rather than hand-rolling markup (`app/CLAUDE.md` Style non-negotiables). `cqw`/`clamp()` was chosen over a Tailwind breakpoint (`@sm:text-xl`, …) because breakpoints react to discrete container-width steps, not to how much text needs to fit — a continuous, container-relative unit is the only way to keep arbitrary-length content on one line without guessing thresholds.
Consequences: `fluid` is additive — every other `SinglePlayerDisplay` caller is byte-for-byte unchanged. Verified against the project's own compiled `global.css` (not a hand-approximation): the exact rendered markup for `current?.expression` fits on one line with no `scrollWidth` overflow at 390px and 320px viewports, for both the widest possible expression (`"501 - 60"`, bounded by `start` ≤ 501 and one dart's max score of 60 in `quick-subtract.module.ts`) and the narrowest (`"2 - 1"`). This is the first use of Tailwind v4 container queries (`@container`, `cq*` units) in the codebase — a reusable pattern for any future big-number display whose content length isn't fixed.

### D326 — Drop the inert `h-full` beside `flex-1`; keep the `max-h-2/5` clamp
Status: Accepted · Date: 2026-09-19
Decision: every `SinglePlayerDisplay` call site that passed `max-h-2/5 h-full` (or `min-h-2/5 max-h-2/5 h-full`) now passes the clamp alone — the nine game interfaces under `components/layout/games/interfaces/`, plus `QuickSubtract.astro`, `DoublePatternPanel.astro` and `SwitchingPanel.astro`, which repeat the same pair. `h-full` is banned beside `flex-1` generally (`07-Frontend/07-Style-Guide.md` §Spacing & layout). The `h-full` *inside* `SinglePlayerDisplay.astro`, on the inner card div, is load-bearing and stays: that div's parent is a plain block box, not a flex container.
Reason: `SinglePlayerDisplay`'s root carries `flex-1 min-h-0` and sits in a `flex flex-col` parent, so `flex-basis: 0%` supplies its main size and the `height: 100%` is never consulted — the percentage resolves against a definite chain (`html`/`body` are `h-dvh max-h-dvh`, D174), so there is no indefinite-height case where `h-full` could act as a fallback. Keeping it implied a sizing contract the box model does not honour, and it was copied into twelve files. The alternative of folding the clamp into `SinglePlayerDisplay` itself was rejected: the same component renders inside `SplitScoreboardHalf.astro` at `size="sm"`, where a 40% cap must not apply, so a built-in default would need a new opt-out prop to undo it at the one call site that matters most.
Consequences: twelve markup files lose one class each; no class was added. The reasoning is spec-level, not measured — the change was made in an environment with no WebKit and no working headless Chromium, so it is unverified on device, exactly as GitHub issue #280 (migrated `FINDINGS.md` F15) warned when it asked for this audit. Issue #280's premise is settled by this: the pair was dead weight, not the cross-browser risk it was suspected of being — the reported iPhone overlap was the nested `glass` stack (D228). The rule is prose in the style guide, not a gate; `scripts/check-style-tokens.sh` has no notion of an element's flex context, so reintroduction is caught by review.

### D327 — The play screen's scoreboard band is one shape, owned by the two shells
Status: Accepted · Date: 2026-09-19
Decision: the region at the top of every play screen is `min-h-2/5 max-h-2/5` — 40% of the play area, identical for one seat and two. `SplitScoreboard.astro` carries it unconditionally; `SinglePlayerDisplay.astro` carries it behind a new `pinnedHeight?: boolean` prop defaulting to `true`, which only `SplitScoreboardHalf.astro` sets to `false` (its card is nested *inside* the band, not the band itself). All 21 call sites — twelve `SinglePlayerDisplay`, nine `SplitScoreboard` — drop their height class and pass none.
Reason: three spellings were live for one region (issue #484): `max-h-2/5` on seven screens, `min-h-2/5 max-h-2/5` on five, and `h-2/5` on all nine `SplitScoreboard` calls, with nothing written down about which a new screen should copy. The third was not a third height but no height at all: `SplitScoreboard`'s root is `flex-1 min-h-0`, so `h-2/5` was inert for exactly the reason D326's `h-full` was, and the two-seat scoreboard has been growing to fill the play area rather than the 40% its author wrote. `min-h-2/5 max-h-2/5` is the spelling that survives on a `flex-1` item, so it is the one that becomes the rule. Owning it in the shells rather than naming a `global.css` primitive was chosen because the geometry is not a look a screen opts into — it is what these two components *are* when used as the region; a primitive class would have left the same 21 repetitions in place under a nicer name.
Consequences: two-seat play screens change visibly — the scoreboard stops filling the play area and sits at 40%, matching the one-seat screens and returning the space to the input surface. Estimated against the 501 two-seat column at 390×844 (the richest content: name, `text-4xl` number, label, checkout chips, three stat rows, leg pill and dot pager) the band's ~292px has roughly 55px of headroom, but that is arithmetic, not a measurement: this environment has no WebKit and its one Chromium build (MDM-managed Edge) crashes headless, so **the two-seat screens need an on-device look before this is trusted** — if a column overflows, the fix is the band's fraction or the column's content, not a per-screen class. `min-h-0` leaves `SplitScoreboard`'s base classes, superseded by `min-h-2/5`. The rule is prose in `07-Frontend/07-Style-Guide.md`; no gate can see an element's flex context.

### D374 — Charts: one portable Chart.js module, glass containers with plain canvases, colors named after CardWrapper's
Status: Accepted · Date: 2026-09-30
Decision: the statistics charts share one module. `modules/ui/chart.module.ts` (`buildConfig`, `ChartView`, HTML tooltip) takes an injected `ChartTheme` and imports no store, token or Alpine; `lib/ui/chart-theme.ts` reads `--chart-<name>` tokens; `lib/ui/chart.data.ts` holds the instance in a closure; `components/ui/Chart.astro` is the glass container with a legend and a table view. V1 is line and bar. A series' color is one of `CardWrapper.astro`'s color names (`sky, violet, rose, teal, emerald, amber, orange, fuchsia, blue`); the default assignment order is `sky, orange, emerald, violet, rose, amber` and is never cycled; a repeated or missing color is a `RangeError`. The canvas is plain; the containers are glass.
Reason: the portable-kit contract (`04-Modules-And-OOP.md`) forbids tokens in `modules/ui`, so the theme is injected. The dataviz validator fails all nine names together on adjacent-pair CVD (`teal`/`emerald`, `blue`/`sky`, `fuchsia`/`rose` are near-twins), so only six are default and the rest are explicit. `CardWrapper`'s free-color escape hatch cannot be validated and is not part of the chart contract. Chart.js breaks behind Alpine's proxy, so the factory passes a JSON-plain copy.
Consequences: `chart.js` is a new dependency, loaded by dynamic import on the statistics page only. Pie/donut and datalabels are deferred until a section needs them. The `--chart-<name>` values are tuned for marks on the black surface and differ from `CardWrapper`'s wash tints; a test keeps the name lists equal. `scoring-trend` is the first consumer; other sections and the heatmap are later cycles.

### D388 — Text is non-selectable by default; selection is an opt-in
Status: Accepted · Date: 2026-10-02
Decision: `global.css` `@layer base` sets `user-select: none` (with the `-webkit-` prefix) and `-webkit-touch-callout: none` on `body`. The same layer restores `user-select: text` on `input`, `textarea`, `[contenteditable]` and the `.select-text` class. Anything a player may need to copy opts in with Tailwind's `select-text` utility; nothing else is touched.
Reason: the app is mobile-first and installed as a web app. A long press on a label, score or button highlighted text and, on iOS, opened the copy/share callout — behaviour of a document, not an app. One base rule fixes it everywhere; per-element `select-none` (as on `DartBoard.astro`) only ever covered the spots someone remembered.
Consequences: desktop browsers lose text selection too; scoping to `@media (pointer: coarse)` is the escape hatch if that is ever wanted. Form fields are exempted explicitly because iOS Safari can block caret placement and paste under an inherited `none`. Existing `select-none` classes stay as harmless no-ops and are not added anew. `.astro`/CSS carry no unit test (D101); the proof is the rule in `global.css`.
Supersedes: none.

### D418 — Native cross-document view transitions between bottom-nav tabs
Status: Accepted · Date: 2026-10-06
Decision: `AppLayout` opts in with `@view-transition { navigation: auto; }` (`navigation: none` under reduced motion) and writes `<html data-tab="<index>">` from `NAV_TABS`/`navTabIndex`. `BaseLayout` emits, only when a tab is set, a classic head script that calls `onTabReveal(event, sessionStorage)` on `pagereveal`: higher tab index adds view-transition type `forward`, lower `back`, equal or unknown skips. `main` (`page`) slides ±20% with fade; `nav` (`bottom-nav`) is static; `.nav-indicator` (`nav-indicator`) glides; the root snapshot is not animated. Timing is `--duration-tab` with `--ease-out`.
Reason: keeps the MPA, Alpine and the auth gate intact. Astro's `ClientRouter` was rejected because it swaps the DOM in one document. Direction uses `sessionStorage`, not the Navigation API, which ships later in Safari. The handler is one self-contained function inlined via `toString()` because bundled module scripts are deferred and can miss `pagereveal`, while the function stays unit-testable.
Consequences: Firefox navigates instantly. Same-tab, reload, first load, `GameLayout` and `login` never animate. Deferred: Speculation Rules prerender, drill-down push/pop, game-screen transitions. CSS carries no unit test (D101); `onTabReveal` and `navTabIndex` are tested, and the browser behaviour was checked in Chromium (every tab pair both ways, reload, setup pages, history back/forward, reduced motion).
Supersedes: none.

### D199 — Board input is press-drag-release with a magnifier, not a tap
Status: Accepted · Date: 2026-08-09
Decision: A `VISUAL_BOARD` dart is captured by press-drag-release on `BoardInputPanel.astro`. `pointerdown` opens `BoardMagnifier.astro` beside the fingertip — a second, unlabelled `DartBoard.astro` clipped to a circle, transformed so the pressed point sits under a crosshair, with the live resolved read below it. The commit happens on `pointerup`; `pointercancel` discards; a press that never moves commits at its own position. The keypad stays rendered for every session as the accessible alternative and is never swapped out for the board.
Reason: The treble ring is ~10 mm tall on a board displayed ~0.65-3.2 px/mm, against a fingertip contact patch nearer 45 px. A bare tap cannot be aimed at that precision and, worse, cannot be *seen* to be wrong before it lands. A misclassified tap does not just mis-render: it writes a wrong `hitZoneKey` and coordinate pair into the fact log, and completed gameplay is immutable, so there is no correction path short of a new record.
Consequences: The pointer surface needs `touch-none`, or the browser claims the drag as a scroll and `pointermove` stops arriving mid-gesture. Magnifier zoom is a multiple of the *displayed* board (`zoom x pxPerMm`, read live from the SVG's screen CTM) rather than an absolute scale, so magnification is constant across viewports. The magnifier is `position: fixed` and clamped against the visual viewport, because its anchor is `clientX`/`clientY`. The whole overlay is `aria-hidden` — it duplicates the read the live text already announces. `BoardMagnifier.astro`'s circle uses an OBJECT-form `:style` binding: Alpine's string form calls `setAttribute("style", ...)`, which wipes the static `--mag-zoom` custom property and silently drops the entire `transform` as invalid, rendering at 1x with every unit test still green.

### D201 — A visual session shows the board in place of the keypad, with markers for the visit's darts
Status: Accepted · Date: 2026-08-09
Supersedes: D199
Decision: While `$store.game.inputModeKey === 'VISUAL_BOARD'`, both play pages hide `ScoreInput.astro` and show `BoardInputPanel.astro` alone. The panel carries its own `Undo dart` control, because the keypad's undo button goes with the keypad. The board draws a marker per located dart of the most recent turn — still open, or just closed by its last dart — so a finished visit's grouping stays visible until the next visit's first dart replaces it. Unseen darts carry no coordinate and are not drawn. Only D199's final sentence is reversed; the press-drag-release mechanism it describes is unchanged.
Reason: Two input surfaces stacked on one play screen read as a broken layout, not as a choice: the board is the session's input, and a keypad below it invites a visit total the player never meant to enter. Markers are what make the board an input a player can check — without them a landed dart leaves no trace, and a mis-aimed one is only discoverable from the running total.
Consequences: The keypad is no longer the always-available accessible alternative on a visual session, which is a real accessibility cost accepted at the owner's direction; the server still accepts a dartless keypad visit inside a visual session, so nothing in the persistence path assumes darts and the fallback can be restored as a per-session toggle without a schema or validator change. Markers render into `DartBoard.astro`'s slot, which overlays the SVG rather than sitting inside it: Alpine's `x-for` needs a real HTML `<template>`, and the HTML parser puts a `<template>` written inside `<svg>` into the SVG namespace, where it has no `.content` and `x-for` cannot clone it. Positions are a percentage of the board's own `-220 -220 440 440` box, so they track the board at any size.

### D202 — Alpine binds at a reactive mirror of the board controller, never at the controller
Status: Accepted · Date: 2026-08-09
Decision: `boardInputData()` publishes a plain `board: BoardView` field and re-copies the controller's readings onto it after every `press`/`move`/`release`/`cancel`/`commitUnseen` call. `BoardMagnifier.astro` binds exclusively at `board`; no view may dereference `input`.
Reason: `boardInput()` is a pure module that keeps `active`, `point` and `placement` in closure variables behind getters. Alpine's reactivity records reads of properties on its own proxies, so a getter over a closure variable is not a tracked dependency: `move()` updated state nothing could depend on. The magnifier appeared on press and then froze — right position, permanently stale content — for the whole drag, which is the exact defect this decision exists to prevent recurring.
Consequences: Every new controller call site must sync, or the view silently stops updating again; the sync is centralised in one `syncBoard()` for that reason. The failure is invisible to Vitest, which never runs Alpine's reactivity — `tests/lib/game/board-input.data.test.ts` guards the mirror's freshness (a snapshot re-read after `move` must differ), and the browser-level behaviour was confirmed by driving the real Alpine build with a pointer drag. The same trap applies to any future pure controller handed to a template.

### D204 — The magnifier's resolved read prints above the circle, smaller
Status: Accepted · Date: 2026-08-10
Supersedes: D199 (its "resolved read below it" placement clause only; the press-drag-release mechanism is unchanged)
Decision: `BoardMagnifier.astro`'s read (`TREBLE 20 · 60`) prints above the magnifier circle at `text-xs` (was `text-sm`, below). `board-input.data.ts` exports a pure `magnifierLabelStyle(view)`, mirroring `magnifierAnchorStyle`/`magnifierBoardStyle`: `top: -(magnifierSize / 2 + gap)px`, paired with a `-translate-y-full` class so the computed `top` lands under the label's own bottom edge rather than its top — the label's height depends on its font size and is never known to the data layer.
Reason: Owner direction after using the shipped board. No architectural tradeoff beyond the geometry note above: `top`, not `bottom`, is required for the same reason `magnifierAnchorStyle` uses `top`/`left` — the anchor div has no explicit size, so any property measured from its own far edge (`bottom`, `right`) would create a circular sizing dependency.
Consequences: `magnifierLabelStyle` is unit-tested directly (mutation-tested: reverting to the old below-placement formula fails both new tests). The visual result was verified by driving the real Alpine build in a headless browser against the project's own compiled CSS, confirming the label's bounding box sits entirely above the circle's.

### D225 — Guest-adding UI ships for 501 only; the runtime guest list is its own component
Status: Accepted · Date: 2026-08-21
Decision: `UserSection.astro` gains an `allowGuests?: boolean = false` prop. Every setup screen except `FiveOhOneSetupForm.astro` calls `<UserSection />` with no prop and renders exactly today's single-owner markup; only 501 passes `allowGuests`. The add-guest button caps the guest list at 3 (`AddGuestButton.astro`'s `x-show="guests.length < 3"`) — 3 guests plus the 1 owner equals the server's `MAX_SEATS = 4` (`services/session-seats.service.ts`). The runtime guest list (avatar, name, remove badge) is its own component, `GuestSection.astro`, rather than markup inlined into `UserSection.astro`'s `allowGuests` conditional.
Reason: `rejectSeatRequest` 400s a second seat for every ruleset but `501_V1` (D08/D220-era seat work), so wiring the button into `UserSection` unconditionally would let a player build a request every other engine rejects; the prop keeps the other eight setup screens byte-identical rather than adding a guard the button itself would never need for 501. The `GuestSection` split exists because of an Astro/Alpine boundary, not a stylistic preference: content written directly inside a `{}` Astro JS expression (a `.map()`/ternary body) must escape Alpine directives as `x-on:click` per this repo's linter exception (`07-Frontend/03-Alpine-Patterns.md`), but a genuinely separate child component's own top-level markup — including its own `<template x-for>` — is not inside that `{}` boundary and can use plain `@click`/`:attr` shorthand. Inlining the guest list's `x-for`/`@click`/`:aria-label` markup into `UserSection`'s ternary would have forced every one of those directives into the escaped form for no reason other than where the file happened to end.
Consequences: adding guest support to a second multi-seat engine is a one-line change at that engine's own `*SetupForm.astro` (pass `allowGuests`), not a `UserSection` edit. `GuestSection.astro`, `AddGuestButton.astro` and `GuestNameModal.astro` are listed in `docs/architecture/07-Frontend/08-Component-Inventory.md` under shared setup shells even though only one caller exists today, because `UserSection`'s prop makes them reusable by construction, not per-game components under the inventory's per-game exclusion. Guest data model (`participantTypeKey: "GUEST"`, side keys `B`/`C`/`D` in add order) is UI-side only in this task — no schema or validator change — composed into `POST /api/sessions`'s existing `participants` array from PR #152's seat work.

### D227 — `IconBtn.astro` is a new component, not a `Button.astro` prop, and is always a true circle
Status: Accepted · Date: 2026-08-21
Decision: `app/src/components/forms/IconBtn.astro` is a standalone component, not an extension of `Button.astro`'s existing `icon` prop. Its base classes always include `aspect-square rounded-full border-3` — `aspect-square` guarantees the button is a perfect circle regardless of what padding the caller passes via `class` (its only sizing input; the component itself applies none), which `rounded-full` alone cannot guarantee once width and height can differ. `border-3` is the base border width for every variant (`primary`/`secondary`/`ghost`/`error`/`dashed`), wider than `Button.astro`'s 1px default, applied uniformly rather than only on `dashed`. `ariaLabel` is a required prop, unlike `Button.astro`'s optional one — an icon-only control has no visible text to fall back to, so omitting it would ship an unlabeled button. One default slot only; no `iconBefore`/`iconAfter`, no `loadingExpr`, no `title`.
Reason: extending `Button.astro`'s `icon` boolean would have kept every icon-only call site paying for `Button.astro`'s text-oriented base classes (`gap-2`, `text-sm font-semibold`, `px-4 py-2.5` conditionally swapped for `p-2.5`) and manual per-call-site `rounded-full`/border overrides — exactly the pattern `AddGuestButton.astro` used before this decision (`variant="dashed" icon class="rounded-full p-3 border-4"`). A new component bakes the icon-only shape in once instead of asking every caller to reassemble it.
Consequences: migrating existing icon-only `Button.astro` call sites (`AddGuestButton.astro`, `GameLayout.astro`'s exit button, `BoardInputPanel.astro`'s undo/bounce-out, `LogoutButton.astro`, `GuestSection.astro`'s remove badge) to `IconBtn.astro` is a separate, explicit follow-up per call site, not automatic — `AddGuestButton.astro` and `GuestSection.astro`'s remove badge migrated the same day this decision shipped (D227's own PR #157, migration in #158), the rest remain on `Button.astro icon` until asked for. `IconBtn.astro` reuses `Button.astro`'s existing `.btn-primary`/`.btn-secondary`/`.btn-ghost`/`.btn-error` CSS from `global.css` — no new CSS rules. D101 (markup-only `.astro` components are test-exempt) applies; no unit test exists for it.

### D187 — Hold UI module instances off the Alpine reactive object
Status: Accepted · Date: 2026-08-07
Decision: An Alpine factory that drives a `modules/ui/*` class keeps the instance in the factory closure, never on `this.*`. The registered `Alpine.data()` name matches the factory call in markup (`toggle`), and the factory file lives under `lib/<domain>/` (`lib/ui/toggle.data.ts`), not in `lib/client/alpine/` which holds only the entry factory and registrars.
Reason: Alpine deep-proxies reactive state, and an ES private field throws when read through a Proxy, so `mount()` / `layout()` never ran and the Toggle pill stayed 0×0. A mismatched registration name fails the same way, silently.
Consequences: `modules/ui` classes are unit-tested with an explicit Proxy guard that documents the hazard. `x-modelable` still exposes scalar reactive fields (`activeTab`), so parent `x-model` binding is unaffected. The Toggle's paired `.astro` deliberately sits in `components/layout/games/setup/` rather than `components/ui/` because it uses app `tab-*` tokens — the same one-directional reading of the pairing rule that `segment-timer.module.ts` already relies on.

### D206 — Throwing-hand preference is a local `$persist` store, not `player_settings`
Status: Accepted · Date: 2026-08-11
Decision: The player's throwing hand (`Handedness`, already a `boardInput()` option per D199) is read from a new `boardInput` Alpine store (`stores/board-input.store.ts`, one `$persist` field, `PersistFactory` per D120) rather than added to the server-backed `player_settings`/`v_player_settings` pair. `board-input.data.ts`'s `freshController` now passes `$store.boardInput.handedness` into `boardInput()` instead of relying on its `"RIGHT"` default, and a new `HandednessForm.astro` on the profile page writes the store directly.
Reason: Which side the magnifier opens on is a per-device rendering preference — it does not describe gameplay, need not sync across devices, and has no server read path today. Routing it through `player_settings` would mean a new migration, endpoint contract bump, service/repository change and view column for a value only the client ever consumes, for no behavioural gain over `$persist`.
Consequences: Handedness does not follow a player across devices (matches D77/D86's `forms/`-as-substitute precedent for pre-`player_settings` local prefs). If a future need for cross-device sync emerges, migrating this one field into `player_settings` is a small, isolated change against an established pattern (`settings.store.ts`/`AppModeForm.astro`) — not a reason to default there now.

### D233 — Unify the dart-preview reveal timer across input modes
Status: Accepted · Date: 2026-08-26

longer branches on `inputModeKey`. Every input mode gets the same 1500ms
delay between a visit resolving and its preview clearing. Bob's 27's

regardless of input mode or seat count. `playPreviewSegments()` (a new
shared export alongside the timer) replaces 3 duplicated segment-computation
functions and reshapes the pre-existing shared `doublesPathPreviewSegments`
helper onto the same gate. See Pattern 19,
`docs/architecture/04-Architecture-patterns.md`.

### D234 — `armHiddenTimer`/`clearHiddenTimer` extracted; all 9 board-input games clear their markers on the shared timer
Status: Accepted · Date: 2026-08-26
Decision: `play-lifecycle.ts`'s reveal-then-clear timer logic is split into two exported primitives, `armHiddenTimer(context, turns)` and `clearHiddenTimer(context)`, factored out of `playCommitDart`/`playUndoVisit`/`runPlayAgain` with no behavior change for existing callers. 501, 121, and Ten Up One Down — whose `commitDart` was otherwise identical to `playCommitDart` (record → mirror → complete-check) — now delegate to it directly, the same way Bob's 27 already does (D233). Score Training calls `armHiddenTimer` directly from `recordDart` instead: its engine can already be complete before a dart is thrown (MINUTES-mode timer expiry via `expireTimer()`), so a post-record `isComplete()` check — which `playCommitDart` always runs — would upload and finish the session mid-visit, on the first dart of a fresh visit. All 9 board-input games now clear their board markers via `playVisitMarkers` on the same 1500ms timer.
Reason: 501/121/TUOD/Score Training never had `hiddenTurnKey`/`hiddenTimer` state at all, so `BoardInputPanel.astro`'s markers — rendered unconditionally by every board-input game — never cleared for these four; a dart's marker sat on the board until the next visit's first dart overwrote the same slot. Extracting the primitive rather than forcing Score Training onto the full `playCommitDart` composite avoids reintroducing the exact class of bug D229 fixed (an unconditional post-record completion check tripping on an already-decided session).
Consequences: `FiveOhOnePlayContext`, `OneTwentyOnePlayContext`, `ScoreTrainingPlayContext`, and `TuodPlayContext` each gain their own `hiddenTurnKey`/`hiddenTimer`/`visitMarkers()` fields, extending the same hand-restated-shape pattern `FINDINGS.md`'s F29 already flags for 5 other `*PlayContext` types (now 9). `docs/architecture/07-Frontend/00-Overview.md`'s Visual Board Input section, which pre-dated most of the 9-game rollout, is corrected to state every ruleset supports `VISUAL_BOARD` and to describe the reveal-then-clear timer instead of the older "stays until the next visit's first dart" behavior.

### D249 — 6 games' `resultsSnapshot` promoted to `{ ...; seats: XSeatResult[] }`; results-modal titles extracted into `resultsTitle()` + shared `matchWinnerName()`
Status: Accepted · Date: 2026-08-30
Decision: Around the Clock, Bob's 27, Doubles Training, 121, Singles Training, and Ten Up One Down's `*ResultsSnapshot` types are promoted from flat/single-seat shapes to `{ ...; seats: XSeatResult[] }` — one stats entry per seat, computed for every seat in the match — matching the shape Five Oh One, Score Training, and Shanghai already used. Each of the 9 games' `*PlayContext` also gains a `resultsTitle(this: XPlayContext): string` method, implemented in its `*-play.data.ts`, replacing the inline `x-text` ternary every results modal (`components/layout/games/result-modals/*.astro`) previously carried; each composes the new shared `matchWinnerName(seats, winningSideKey)` helper (`app/src/lib/game/match-result-text.ts`) with that game's own title wording. Singles Training's `resultsTitle()` reads the owner's own per-seat `resultsSnapshot.seats[…].status` rather than a top-level field, since its HARD/EXTREME elimination can resolve one seat WON and the other LOST from the same match. Bob's 27's modal collapses its prior two-sibling-`<h2>`/`x-show` pattern into the same single `x-text="resultsTitle()"` call as every other game, a deliberate, spec-approved change to its pre-completion default text (was a static "Match Summary", now evaluates the same ternary as post-completion and falls through to "Winner!" since Bob's 27 has no tie/no-winner branch).
Reason: `docs/superpowers/specs/2026-08-22-single-opponent-seat-remaining-engines-design.md` wired 1v1 support into every engine, but its own scope/touch-list never named the snapshot-shape change these 6 games' results modals actually needed at the data layer — so they kept computing stats for the owning player only, silently dropping the opponent's data before it ever reached the UI, not merely failing to render it. Separately, every modal's title ternary had grown an unreadable, untested inline expression (`docs/superpowers/specs/2026-08-30-result-modal-consolidation-design.md` Issue 2) repeating the same `$store.game.seats.find((s) => s.sideKey === winningSideKey)?.displayName` lookup nine times over.
Consequences: `SinglePlayerSummary.astro`/`ComparisonSummary.astro` (D-adjacent, see `docs/architecture/07-Frontend/08-Component-Inventory.md`) and `resultsTitle()`/`matchWinnerName()` are now the canonical results-modal patterns — a new game's results modal uses both from the start rather than hand-rolling either. Bob's 27's 1v1 completion path also picked up a latent fix in the same pass: `status` now reads the match-level `state.status` instead of any one seat's own in-progress status, so a seat that wins purely because the opponent busted is no longer misreported as `"LOST"`. See Pattern 18, `docs/architecture/04-Architecture-patterns.md`, and `docs/architecture/07-Frontend/03-Alpine-Patterns.md`'s Results-Modal Title Pattern section.

### D251 — Checkout-hint visibility is one shared client-only `$persist` toggle, not a `player_settings` field or per-game config
Status: Accepted · Date: 2026-08-31
Decision: Whether 501, 121, and Ten Up One Down show a suggested checkout route is controlled by a single boolean, `checkoutHints.enabled`, held in a new `checkoutHints` Alpine store (`stores/checkout-hints.store.ts`, one `$persist` field, `PersistFactory` per D120), defaulting to `true`. All three games' setup screens share the same `Switch.astro` control (`x-model="$store.checkoutHints.enabled"`); there is no per-game-type override. `FiveOhOnePlayContext["$store"]`, `OneTwentyOnePlayContext["$store"]`, and `TuodPlayContext["$store"]` widen to add an optional `checkoutHints?: { enabled: boolean }` field rather than making it required on the shared `PlayStoreContext<TConfig>` generic all 9 games use, so the other 6 rulesets' `$store` types and tests are untouched. Each game's `checkoutHint()`/`checkoutHintFor(seatRef)` getter gates on `this.$store.checkoutHints?.enabled === false` returning `""`; TUOD had no such getter before this decision and gains one (`checkoutPathFor` keyed off `currentTarget` instead of `remainingScore`).
Reason: which side shows a checkout suggestion is a per-device display preference, not gameplay data to persist server-side — the same reasoning D206 already established for `boardInputStore`'s handedness field. A `player_settings` round-trip (migration, endpoint, service/repository, view column) buys no behavioural gain over `$persist` for a value only the client ever reads. One shared toggle rather than three per-game ones matches how the feature request (issue #203) was scoped, and avoids three near-identical settings rows for the same underlying concern. The field is optional rather than required on `PlayStoreContext` because roughly 90 existing test call sites across the three affected `*-play.data.test.ts` files (and, for TUOD, every inline `$store` object literal with no `as TuodPlayContext` cast) would otherwise need editing solely to add a field their own tests never exercise.
Consequences: a player who wants hints off during 501 but on during TUOD cannot — the design's explicit rejected alternative — and gets one shared toggle instead. The preference is per-device, not per-account: it does not follow a player across devices, matching D206's precedent. `docs/superpowers/specs/2026-08-31-checkout-hints-toggle-design.md` documents the two other rejected storage locations (session-config override, `player_settings`) and their costs in full. `FINDINGS.md`'s F46, raised during this task, is unrelated (a stale style-guide/component-inventory reference to nonexistent `Checkbox.astro`/`Radio.astro` components) and not acted on here.

### D260 — Pause/resume on the 3 MINUTES-countdown rulesets is one persisted `timerPaused` flag plus one shared toggle in `play-lifecycle.ts`, never read by an engine
Status: Accepted · Date: 2026-09-07
Decision: Score Training, TUOD, and 121 (`_V2`) each gain a Pause/Resume icon toggle next to their existing MINUTES countdown label. `game.store.ts` gains `timerPaused: boolean` (own `persist()` call per D120, defaulting `false`, reset by both `startSession()` and `reset()`); `PlayStoreContext<TConfig>["game"]` widens with the matching optional field. `play-lifecycle.ts` gains one shared `playToggleTimerPause(context: PlayLifecycleContext<...> & { timer: SegmentTimer | null })`: a no-op without a live `timer` or once `finished`, otherwise `timer.stop()` + `timerPaused = true` when running, or `timer.start()` + `timerPaused = false` when already paused — `SegmentTimer.stop()`/`start()` already preserve `remaining`, so no `SegmentTimer` change was needed. The same module's two shared choke points, `playCommitDart` and `playRunBotVisualBoardVisit`, both become no-ops while `$store.game.timerPaused` is true (the latter re-checked mid-visit, both before and after the bot's pre-throw delay, so a pause mid-throw stops the bot cleanly rather than completing one more dart). Each of the three games' own `submitVisit`/`recordDart`/`undoVisit`/`maybeRunBotVisit` methods add the identical `|| this.$store.game.timerPaused` guard clause (TUOD's `recordAttempt` too), and each's `init()` stops a freshly-rebuilt timer immediately if the store says it was already paused before the reload — the field is ephemeral client state, `$persist`-ed for reload continuity only, never uploaded as part of the events batch and never read by any engine. `BoardInputPanel.astro`'s wrapping `x-show` gains `&& !$store.game.timerPaused` alongside its existing `!finished` clause, hiding the pointer surface, undo, and bounce-out together with the keypad. Two new icons (`icons/pause.svg`, `icons/play.svg`) render through the existing `Button` primitive, mirroring every other standalone action in these games' templates.
Reason: Feature request to let a player step away mid-session without either losing progress (abandon) or having the countdown keep running unattended. `SegmentTimer.stop()`/`start()` already round-trips `remaining` correctly, so the whole feature is wiring a boolean through the existing choke points rather than any change to the timer primitive itself. Centralizing the toggle in `play-lifecycle.ts` (rather than three hand-rolled copies) and gating both shared choke points there means a fourth MINUTES-mode game only needs to pass its own `timer` field through, not re-derive the stop/resume/guard logic. `OneTwentyOnePlayContext` needed an explicit `togglePause(this: OneTwentyOnePlayContext): void` method signature added to its own hand-written type (not needed for `ScoreTrainingPlayContext`/`TuodPlayContext`, whose otherwise-identical `*.data.test.ts` files build their test doubles by spreading `{ ...xPlay() }` with no `as XPlayContext` cast at the call site) — a concrete instance of `FINDINGS.md`'s F29 (these three types hand-restate `PlayLifecycleContext`'s shape instead of reusing it) actually biting during this task.
Consequences: adding the `timerPaused` guard inline to `init()`'s existing MINUTES branch pushed both Score Training's and TUOD's `init()` over `npx fallow`'s per-function complexity threshold (TUOD's `submitVisit` too, from its own added guard clause); both files' `init()` now delegate to a local `maybeResumeCountdown(game, config, engine)` helper 121 already had reason to use (its own `init()` was structured this way from D243 onward), and TUOD's `submitVisit` extracts its guard into a `canSubmitVisit(context)` predicate mirroring the existing `canReplay()` precedent in `one-twenty-one-play.data.ts` — no behavior change, confirmed by the full existing test suites passing unchanged plus the new pause/resume cases. `OneTwentyOne.astro` gained a standalone countdown-label block (identical in shape to Score Training's/TUOD's own) between its solo and split-view templates; the implementation plan described this block as already present for the 1v1 (`SplitScoreboard`) case pending only a button addition, but no such block existed in the file at execution time — the plan's assumption did not hold, so the block was added fresh rather than edited in place. Manually verified in a running dev server (browser-driven, network layer mocked for `/api/sessions/active` and `/api/auth/**` since this session's container has no live Neon connection): the countdown freezes exactly at pause, the keypad disables, resume continues from the same remaining time, and a reload while paused stays paused. Full design and implementation plan: `docs/superpowers/specs/2026-09-07-pause-resume-timed-modes-design.md`, `docs/superpowers/plans/2026-09-07-pause-resume-timed-modes.md`.

### D269 — Balanced Training's Finishing step populates the real global `$store.game` rather than forking `TenUpOneDown.astro`/`BoardInputPanel.astro`
Status: Accepted · Date: 2026-09-12
Decision: `balanced-training-play.data.ts`'s Finishing step reuses the existing standalone TUOD play UI unmodified. Its `startFinishingStep()` helper calls `self.$store.game.reset()` then `self.$store.game.startSession({...})` with the just-created Finishing `exercise_sessions` row's own `sessionId`/`gameTypeKey`/`rulesetVersionKey`/mode pair and a `configSnapshot` built from the step's resolved configuration plus an empty `seats: []`, exactly as a standalone TUOD session would populate it. A new `finishing-step.data.ts` wraps the real `tuodPlay()` unchanged — `finishingStep(onStepComplete)` overrides only `uploadAndCompleteSession()` to call through to TUOD's own implementation and then `onStepComplete()` (the routine's `completeCurrentStep()`), gated by `this.currentStep()?.exerciseTypeKey !== "GAME"` so the routine-level `completeSession()` call does not fire a second, redundant PATCH for a step `tuodPlay()` already completed itself. `play/index.astro` mounts the wrapped store as a nested `x-data="finishing"` inside the routine's own `x-data="balancedTrainingPlay()"` scope; neither scope carries an `x-init` directive — Alpine calls a data factory's own `init()` method automatically once mounted, which is what lets the nested Finishing scope's own `tuodPlay()` reconciliation (`fetchActiveSessions()` + `reconcileActiveSession()`) run with `$store` correctly injected, after `$store.game` has already been populated by the parent's `startFinishingStep()` call.
Reason: `docs/superpowers/specs/2026-09-12-balanced-training-playable-design.md` §6 mandates reusing the existing TUOD play UI "in place" rather than building a dedicated in-routine screen, but its own text stopped short of resolving the one real obstacle this creates: `TenUpOneDown.astro`/`BoardInputPanel.astro` read `$store.game` as Alpine's registered global store, not a prop or a locally-scoped object, so nothing short of forking both components could point them at a routine-local copy instead. Populating the real global store costs nothing extra since a player can never have a standalone TUOD game and a Balanced Training routine's Finishing step active at the same time, and `$store.game.reset()` already exists for exactly this kind of handoff.
Consequences: the Finishing step's own completion must route through TUOD's unmodified `uploadAndCompleteSession()` rather than the routine's shared `completeSession()` call every other step (Warm-Up, Switching, Double Pattern) uses — `completeCurrentStep()` carries one `exerciseTypeKey !== "GAME"` branch as the one place this asymmetry is visible. Should this repo later ever let one player run two TUOD-shaped sessions concurrently (a standalone game alongside a routine's Finishing step), this decision would need revisiting — no such case exists today. Full design and implementation plan: `docs/superpowers/specs/2026-09-12-balanced-training-playable-design.md`, `docs/superpowers/plans/2026-09-12-balanced-training-playable-implementation.md`.

### D270 — Warm-Up's timer no longer auto-starts; a "Let's play!" tap unlocks audio first
Status: Accepted · Date: 2026-09-13
Decision: `balanced-training-play.data.ts`'s `startCurrentStep()` no longer calls `startWarmUpTimer()` from its `WARM_UP` branch — it only calls `buildWarmUpEngine()` and sets two new fields, `warmUpReady = false` and `warmUpConfiguration = result.configuration`. A new `confirmWarmUpReady()` method (no-op if already ready or if `warmUpConfiguration` is unset) flips `warmUpReady` to `true` and calls `startWarmUpTimer(this.warmUpConfiguration)`. `WarmUpPanel.astro` renders two `x-if` branches on `warmUpReady`: `false` shows a centered "Are you ready?" title plus a `Button` titled "Let's play!" wired `@click="confirmWarmUpReady()"`; `true` shows the existing count-up display and dartboard highlight, unchanged. `SegmentTimer` (`app/src/modules/ui/segment-timer.module.ts`) gains a public `unlockAudio()` method — `playBeep()`'s existing suspended-context check is factored out into a shared private `resumeIfSuspended(ctx)` used by both — and `startWarmUpTimer()` calls `this.warmUpTimer.unlockAudio()` immediately after constructing the timer, before `.start()`.
Reason: the Warm-Up phase-change ping (`docs/architecture/09-Training/01-Routines.md` §16; spec'd in `docs/superpowers/specs/2026-09-11-training-page-and-balanced-training-design.md` §6.1) never played. `SegmentTimer`'s `AudioContext` was created and `resume()`-d lazily from inside a `setInterval` tick, on a timer that was itself started automatically by Alpine's `init()` lifecycle hook (no click involved) after two awaited network round-trips. Browser autoplay policy only lifts a suspended `AudioContext` when creation/`resume()` runs synchronously inside a real user-gesture handler; nothing in that chain qualified, so commit `63e0b2a`'s earlier "resume before beep" fix addressed the state check but not the timing, and stayed silently broken. The Warm-Up screen was deliberately built with zero on-screen interaction (`docs/superpowers/specs/2026-09-12-warmup-play-interface-design.md`, "no button, no text"), and this app has no `ClientRouter`/view-transitions, so the routine's own "Start" button — on a separate page, one full navigation earlier — can't carry a gesture forward either. A single deliberate tap on the Warm-Up screen itself was chosen over the alternatives considered: moving the unlock onto the previous page's Start button (would require replacing full-page navigation with a client-side transition for this one flow) or leaving it best-effort on browsers' Media Engagement Index heuristics (unreliable, not acceptable for a training cue).
Consequences: supersedes the "no button, no text" Warm-Up screen design from `docs/superpowers/specs/2026-09-12-warmup-play-interface-design.md`/`-implementation.md` (both `docs/superpowers/specs/**` — historical, left unedited per `docs/CLAUDE.md`). Every other `SegmentTimer` consumer already starts from a real "Start" button click (Score Training, TUOD, 121, Quick Subtract) and is untouched by this decision; whether any of them can be reached without a preceding click, reproducing the same silent-audio defect, was not investigated here. `app/tests/modules/ui/segment-timer.module.test.ts` gains a direct `unlockAudio()` test; `app/tests/lib/training/routines/balanced-training-play.data.test.ts`'s three existing Warm-Up cases that asserted the timer already running right after `init()` now call `confirmWarmUpReady()` first, plus two new cases cover the gating (`warmUpTimer` stays `null` until confirmed) and the audio-unlock call itself (`SegmentTimer.prototype.unlockAudio` spy).

### D278 — One page-level `AudioContext` and one routine-wide `SessionClock`, surfaced through a `trainingSession` store in the layout header
Status: Accepted · Date: 2026-09-14
Decision: audio moves out of `SegmentTimer` into `modules/ui/audio-cue.module.ts`, which owns a single lazily-created `AudioContext` for the page and exports `unlockAudioCues()`, `playAudioCue(frequency, duration)` and `resetAudioCues()`; `SegmentTimer.unlockAudio()`/`playBeep()` now delegate to it and the class holds no context of its own. `balanced-training-play.data.ts` additionally plays an explicit step-change cue (660 Hz, 0.25 s) whenever a step other than the routine's first opens. A new `modules/ui/session-clock.module.ts` (`SessionClock`) is one open-ended count-up started by whichever step runs first (`startSessionClock()` is idempotent, called from `startWarmUpTimer`, `startStepTimer` and `startFinishingStep`) and stopped only when the routine completes or is abandoned; its elapsed seconds are derived from `Date.now()` rather than counted per tick. A new non-persisted `stores/training-session.store.ts` holds `active`, `elapsedSeconds` and `stepKey`, and derives `headerLabel` (`"00:38 - warm up"`, with `WARM_UP`/`SWITCHING`/`DOUBLE_PATTERN`/`GAME` reading as warm up / switching / doubles / finishing). `play/index.astro` swaps `gameTitle="Balanced Training"` for `gameTitleExpr="$store.trainingSession.headerLabel"`.
Reason: three defects with one shape. (a) Each `SegmentTimer` created its own `AudioContext`, so D270's gesture unlocked only the Warm-Up timer's — every later step's timer built a fresh suspended context and stayed silent, which is why cues were heard between warm-up phases but never between exercises. A context is unlocked per page, not per object, so one shared context makes a single gesture cover every later cue. (b) Each step had its own clock and none spanned the routine, so nothing could show total session time. `SessionClock` is a separate primitive rather than a `SegmentTimer` mode because `SegmentTimer` is defined by a total it counts toward and completes at, which a routine-wide clock has not got. (c) The header renders inside `GameLayout`'s own `x-data="gameLayout()"` scope, an ancestor of the page's `x-data`, so an expression there cannot reach a page component's members — `$store` is the only binding both scopes share.

### D184 — The decision ledger is a router plus domain files, not one document
Status: Accepted · Date: 2026-08-02
Decision: `DECISIONS.md` holds only front-matter, the authority note, the Source key, a routing table, the Deferred list, and the rules for adding a decision. All decisions live in `decisions/**`, one file per ownership domain, each carrying `load-when` / `depends-on` / `related` front-matter.
Reason: At 163 decisions / 65 KB the single file cost every task the entire project history; a frontend task loaded 27 API and 14 database decisions it never read.
Consequences: Decision IDs stay frozen (`D01`–`D183`) because ~180 citations reference them by ID, not location, so the split required no citation edits. Decisions from D184 on use a block format with Reason/Consequences; the 163 migrated rows keep their original terse table form permanently, since back-filling rationale nobody recorded would mean inventing it. `scripts/check-decision-ids.sh` enforces uniqueness, no-disappearance, `Supersedes:` resolution, and a row-free router.

### D185 — Graph freshness is CI-owned; the local CLI is optional
Status: Accepted · Date: 2026-08-03
Decision: Knowledge-graph freshness is owned by CI, not by each agent/clone. `.github/workflows/graph.yml` rebuilds `graphify-out/graph.json` on every push to `main` (`GRAPH_REFRESH_STRICT=1`) and opens/updates a PR carrying the rebuild, since `main` is protected and the workflow cannot push directly to it; on pull requests it posts a non-blocking delta comment instead. Installing the `graphify` CLI locally remains optional, for `graphify query/path/explain` while working, and is no longer a per-clone requirement.
Reason: `scripts/refresh-graph.sh` exited 0 whenever the CLI was absent, so any clone that skipped the manual install silently skipped the rebuild too — four consecutive branches (score-training configurable-duration, bottom-nav iPhone Home Screen fix, 501-recreational-v1, decision-ledger-split) shipped knowledge-graph-staleness disclosures instead of a refreshed graph. By the time this was corrected, the committed graph had drifted to 2,321 nodes / 2,762 links against 2,872 / 4,085 on a clean rebuild, and its `built_at_commit` (`391d2dd`) was no longer reachable in history.
Consequences: `GRAPH_REFRESH_STRICT=1` makes a broken CI install fail the workflow loudly instead of no-op-ing the way the local default does. Delta comparison must normalise `built_at_commit` away as the sole volatile field, or every run would register as dirty even with no real content change. A hard-blocking PR gate on graph freshness was considered and rejected: it would make graphify CLI availability a prerequisite for contributing at all, which is the exact assumption that had already failed to hold across four branches.

### D186 — Opening the graph-refresh PR depends on a repo setting; the workflow degrades instead of failing
Status: Accepted · Date: 2026-08-05 · Refines: D185
Decision: `graph.yml`'s `refresh` job treats PR creation as best-effort. It always rebuilds, commits and force-pushes `chore/graph-refresh`; if `POST /pulls` returns 403 "GitHub Actions is not permitted to create or approve pull requests" it emits a warning plus a run summary carrying the branch, a `compare` link and the delta, and finishes green. Any other error from that call still fails the job. Full automation requires *Settings → Actions → General → Workflow permissions → "Allow GitHub Actions to create and approve pull requests"*, which is off by default on GitHub.
Reason: measured on the first real post-merge run (run 30978978985, 2026-08-05). Every step succeeded — rebuild, the normalised gate, the commit, the force-push — and only the PR-open step 403'd, because `GITHUB_TOKEN` cannot open pull requests unless that repo setting is enabled. D185 asserted the job "opens/updates a PR" without recording that this is contingent on a setting the workflow cannot control.
Consequences: with the setting off, the refreshed graph still lands on `chore/graph-refresh` and needs a one-click manual PR; the run stays green so `main` is not painted red on every merge, since a permanently-red required check is noise that gets ignored — the same not-noticing that let the graph go stale for four branches. The cost is that the pending branch is visible only in the run summary, so the setting is the preferred fix and the fallback is the safety net. Failing the run was rejected for the noise reason; silently succeeding with no summary was rejected because the waiting branch would be invisible.

### D194 — A gate that can silently find nothing is not a gate
Status: Accepted · Date: 2026-08-08
Decision: `scripts/check-context-map.sh` pins `LC_ALL` to an available UTF-8 locale before its migration-range check, and warns loudly when none exists. That check is also narrowed: `decisions/**` is excluded from it entirely, and lines naming seeds are skipped.
Reason: the range pattern matches a U+2013 en-dash. Under the POSIX/C locale that character is three bytes, its continuation bytes consume the pattern's `.?` slots, and every range stops matching — so the check passed by finding nothing rather than by finding nothing wrong. CI runs in a UTF-8 locale and did match, which is how six stale ranges reached PR #73 after the gate had been reported green locally on every run of the branch. A checker whose failure mode is silence is worse than no checker: it converts an unverified claim into a reported pass.
Consequences: the exclusions resolve a real contradiction between two gates. `check-decision-ids.sh` hashes every migrated decision row so it can never be edited, while this check demanded that D21's `chain 0001–0016` follow the chain forward — both could not hold, and the ledger is the side that must not move, because a decision records what was true when it was made. Seed ranges are skipped because seeds carry their own numbering that the migration chain max says nothing about; `docs/architecture/README.md`'s `seeds 0001–0006` was being reported as a stale migration range. Any future gate whose matching depends on non-ASCII text must pin its locale the same way, or it inherits this failure mode.

### D213 — The context map routes; it does not carry the record
Status: Accepted · Date: 2026-08-19
Decision: `00-Context-Map.md` is reduced to a router (context packs, authority order, maintenance protocol). The canonical file inventory moves to `00-File-Inventory.md`, loaded only when a pack falls short; version history, per-task `docs/superpowers/**` rows and Current Implementation State move to `00-Context-Map-History.md` (`status: historical`), which no task loads. `AGENT.md` stops mirroring `CLAUDE.md` and becomes a fixed pointer stub, with `scripts/check-agent-mirrors.sh` inverted to assert the stub. The `Tool Allowances & Restrictions` sections are deleted from all six `CLAUDE.md` files.
Reason: the map was 37.6k tokens and the root `CLAUDE.md` protocol opened it at the start of every task, while the packs it routes to budget 2–18k — the router cost 2–10x the payload. 28.5k of it (76%) was provenance: a single 75k-character version-history line, 57 rows describing point-in-time specs and plans, and drift-prone status prose. No gate ever wanted them — `check-context-map.sh` check 4 only requires top-level `docs/architecture/*.md` files be registered. The six `AGENT.md` files were byte-identical copies enforced identical by a gate, taxing every rule edit twice. The tool-allowance prose bound nothing: Claude Code enforces tool access through `.claude/settings.json`, and the prose was already contradicted by practice, restricting `mcp__github__*` in a repo whose workflow is issue-to-PR.
Consequences: the per-session context floor drops from ~39.3k to ~3.0k tokens. Nothing is deleted — every relocated token still exists in an unloaded file. Four gate scripts had to move with the split: `check-context-map.sh` registers against the inventory, `check-context-budget.sh` reads packs from the map and file rows from the inventory, `check-doc-links.sh` skips the path-backtick pass for `status: historical` documents (the carve-out `decisions/**` already had, for the identical reason), and `check-agent-mirrors.sh` asserts the stub instead of the mirror. No new gate script was created, so `.github/workflows/quality.yml` and `.husky/pre-commit` are unchanged. Future context growth lands in the history archive, which is written on every task and read on none. The graph rule in root `CLAUDE.md` — instructing agents to query a CLI that is absent from the session container — is knowingly left standing for a later change.

### D214 — A finding is logged, not fixed; acting on one needs permission
Status: Accepted · Date: 2026-08-19 · Supersedes: D107
Decision: Anything an agent notices that its task was not asked to change is appended to a new root `FINDINGS.md` and named in the completion report, never fixed in the same pass; acting on a finding requires explicit user permission and becomes its own task on its own branch. The rule is a root `CLAUDE.md` Hard Invariant, the log is shape-guarded by `scripts/check-findings-log.sh` (gate 16, in `.husky/pre-commit` and `quality.yml`), and `context-maintenance` step 8 becomes the Findings gate. Findings are deleted when resolved, and ids come from a `highest-issued:` high-water mark rather than a scan.
Reason: an agent that found a defect mid-task had three bad options and no good one — widen the diff past its assignment, mention it in chat where the record dies with the session, or park it in `DECISIONS.md`'s Deferred list, where five deliberately-unbuilt features and a known-broken script were filed under one heading. Five live contradictions were sitting unrecorded in the repo when this was written, every one found incidentally during earlier tasks. D107's self-learning gate already encoded propose-then-confirm but only for `CLAUDE.md`/`AGENT.md` rule sharpenings, and half its target went dead when D213 reduced every `AGENT.md` to a pointer stub; a stale doc or a bug outside scope is not a rule sharpening, so it never fired for any of the five.
Consequences: the per-session context floor rises from ~3.2k to ~3.4k tokens — the only floor increase in the change, accepted because a non-negotiable rule belongs where every task already reads. `FINDINGS.md` cannot grow into a provenance blob the way the pre-D213 context map did, because resolved entries are deleted rather than restatused; the cost is that a finding's history after deletion is git history alone, plus a `decisions/**` entry where the fix embodied a real choice. The gate proves the log's shape and that every cited evidence path still resolves; it cannot prove an agent logged instead of fixed, and no script can — the invariant carries that obligation. The log ships seeded with F1–F5 and none of them fixed, F3's one-word correction included: a rule that yields to convenience on its first pass is read as advisory forever after.

### D223 — The type gate fails on hints; done means 0 errors, 0 warnings, 0 hints
Status: Accepted · Date: 2026-08-21
Decision: `npm run check` runs `astro check --minimumFailingSeverity hint`, so any hint-level diagnostic — an unused import, an unread parameter — exits non-zero, and `.github/workflows/quality.yml`'s Type gate invokes that script instead of calling `npx astro check` directly. The definition of done for `app/` work is that every step of `validate:app` exits zero, `npx fallow` included, and the type gate reports 0 errors, 0 warnings, 0 hints. The bar is stated in `app/CLAUDE.md` and the `validate-app` skill; the fix for a hint is to delete the dead declaration, never to suppress it.
Reason: `astro check`'s default `--minimumFailingSeverity error` printed hints and then exited zero, so three unused declarations had accumulated across `src/` and `tests/` while every task truthfully reported the gate green. Reporting a diagnostic that cannot fail anything trains agents to read the summary line as decoration. CI compounded it by running the bare binary rather than the package script, so hardening the script alone would not have reached the pipeline. The same pass fixed `npx fallow`, red on the baseline (F12) because `foldFiveOhOneState` breached the cognitive-complexity ceiling: two gates that could not go green had made `validate:app` unrunnable end to end, which is the condition under which a completion bar stops being one.
Consequences: dead code cannot accumulate behind a passing gate. Every future task pays the cost of deleting unused declarations before it can claim done, and an agent removing the last use of an import must remove the import in the same pass. `--minimumSeverity` stays at its default so hints are still printed; only the failing threshold moved. The 71 clone groups `fallow dupes` reports (14.9% duplication) remain non-gating: `duplicates.threshold` is unset, `fallow dupes` exits zero on its own, and the deliberate `*-play.data.ts` duplication D215 accepted is untouched by this decision.

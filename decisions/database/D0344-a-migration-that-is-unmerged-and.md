# A migration that is unmerged and provably pending everywhere is corrected in place; `0041`'s `day_count` is `::int`

## Context and Problem Statement
`count(*)` is `bigint` and node-postgres returns `int8` as a string, so `day_count` reached `TrainingScheduleRow.dayCount: number` and `ScheduleSummary`'s `z.number().int()` as `"3"` — issue #538. Fixing it where it is wrong keeps the two aggregates in one view consistent and leaves one statement of the view's shape; an `0042` that recreated the view to change one cast would have made the chain's own history misleading about what was ever deployed, for a view no environment had yet built. The invariant exists because an applied migration's edit silently diverges the chain from every database that already ran it — a condition `db:status` can disprove, which is what turns "treat it as non-editable because this sandbox cannot tell" (the wording D339/D342 landed under, from a sandbox with no database) into a question with an answer.

## Decision Outcome
Chosen option: "`0041`'s `v_training_schedules.day_count` gained the `::int` cast its sibling `routine_minutes` already had, edited into `0041` itself rather than added by an `0042` that would drop and recreate the view one commit after creating it. The edit was made under a narrow carve-out to "never modify applied migrations": a migration may be corrected in place only while it is (a) still unmerged, on its own PR branch, and (b) shown pending by `npm run db:status` *and* `npm run db:status:prod` — both were run on 2026-09-20 and both reported `0041` pending, 40 applied. Once either proof is unavailable — no `DATABASE_URL`, or the branch has landed — the migration is non-editable as before. `0041` was applied to the Neon dev branch immediately afterwards, so it is now closed to further in-place edits, and root `CLAUDE.md`'s invariant is rewritten around the carve-out rather than around `0040`/`0041` by name.".

### Consequences
`day_count` is `integer` in `pg_attribute` and arrives as a JS number, verified against the live view; `database/verification/0041_training_schedule_checks.sql` ran in full for the first time on the Neon dev branch and reported ALL 9 CHECKS PASSED, closing the open item D342 recorded. The carve-out is deliberately proof-bound, not judgement-bound: an agent without a `DATABASE_URL` cannot satisfy (b) and therefore cannot use it, which keeps the sandbox behaviour D339/D342 assumed exactly as it was. `app/src/db/schema.ts` was regenerated by `drizzle-kit introspect` against the migrated database in the same pass (issue #537), so the branch no longer ships a Drizzle mirror one migration behind its chain.

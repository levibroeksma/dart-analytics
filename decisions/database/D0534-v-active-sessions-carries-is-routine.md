# `v_active_sessions` carries `is_routine_step` and `configuration`; the repository join is gone

## Context and Problem Statement
D442 kept a runtime join of `exercise_sessions` and `exercise_configurations` in the repository only because `schema.ts` could not be edited in the workspace that built the resume deck, and said it stays until the two fields are in the view. That split the read model between a view and an ad-hoc join every new consumer had to repeat. `exercise_configurations` is unique per session, so the join adds no fan-out. Closes #893.

## Decision Drivers
* D442 kept a repository join only because `schema.ts` could not be edited in the workspace that built the resume deck, and said it stays until the two fields are in the view.
* The join split the read model between a view and an ad-hoc join every new consumer had to repeat.
* `exercise_configurations` is unique per session, so the join adds no fan-out.

## Considered Options
* Keep the runtime join in the repository.
* Recreate `v_active_sessions` with `is_routine_step` and `configuration` (chosen).

## Decision Outcome
Chosen option: "migration `0054_active_sessions_resume_fields.sql` recreates `v_active_sessions` with two trailing columns: `is_routine_step` (`routine_step_sequence_number IS NOT NULL`) and `configuration` (the `exercise_configurations` snapshot, NULL if none, via one `LEFT JOIN`). `findActiveSessions` selects from the view alone.".

### Consequences
the API shape of `GET /api/sessions/active` is unchanged. `schema.ts` regenerated by `db:introspect`. Verification: `database/verification/0054_active_sessions_resume_fields_checks.sql` (4 checks) on a scratch Postgres 16.

### D189 — Engines branch on VISUAL_BOARD input mode; 501 bust visibility becomes mode-scoped
Status: Accepted · Date: 2026-08-05
Decision: `EngineInputMode` distinguishes capture depth inside 501 and Score Training: under ANALYTICS + VISUAL_BOARD, each engine records dart-level visits (`classify(x, y)`'s hit target/zone/score/coordinates folded onto every dart, no game-specific point derived from it), while QUICK_SCORE keeps recording turn-total-only visits with no dart rows, unchanged. `isVisualBoardCapture(captureModeKey, inputModeKey)` (`app/src/services/rulesets/visual-board.validator.ts`) is the single predicate both the Worker validator and the engines key on. The Worker re-derives every submitted dart from its own coordinate via the shared `classify()` and refuses the batch on any disagreement with the client's claim — the client's zone/target/score are computed for immediate feedback but never trusted as authority.
Reason: The QUICK_SCORE 501 bust-vs-scoreless-visit ambiguity (`06-Spec/04-Runtime-Layer.md`'s known limitation) is a capture-depth problem, not a 501-specific one: full dart rows make the two cases distinguishable by construction — counted `0` against thrown non-zero darts — so the fix belongs to input mode, not to a schema change or a 501-only special case.
Consequences: `06-Spec/04-Runtime-Layer.md`'s known-limitation section is retitled to scope it to QUICK_SCORE and gains a "Retired for VISUAL_BOARD sessions" note. `DartZoneKey`'s `INNER_SINGLE`/`OUTER_SINGLE` split (D191) is a precondition — without banded singles, a visual dart landing in either band would score correctly but classify to an unbanded zone the intended-vs-hit accuracy analysis could not distinguish by ring side. A VISUAL_BOARD session's busted visit persists `turns.total_score = 0` alongside dart rows carrying their real non-zero board scores (the `total_score` bust carve-out, `06-Spec/04-Runtime-Layer.md`) — that divergence is the fact the mode-scoped fix depends on. QUICK_SCORE sessions remain unfixable: completed gameplay is immutable and no coordinate exists to recover.

### D197 — `validateConfig` must admit every mode pair its `validateBatch` handles
Status: Accepted · Date: 2026-08-08
Decision: `fiveOhOneValidator.validateConfig` and `scoreTrainingValidator.validateConfig` accept `ANALYTICS + VISUAL_BOARD` as well as `RECREATIONAL + QUICK_SCORE`, via the shared `isQuickScoreOrVisualBoardCapture` predicate in `services/rulesets/quick-score.validator.ts`. Both had hard-rejected anything but quick score while their own `validateBatch` already routed visual-board turns to `validateVisualBoardTurns`. A ruleset validator's config gate and its batch gate must admit the same set of mode pairs; the two halves are one statement of what the engine supports, not two independent checks.
Reason: `validateConfig` runs at session creation, before any batch exists. D189 wired the batch path only, so the visual capture path could be validated but never entered — every attempt to start a 501 or Score Training session in `ANALYTICS + VISUAL_BOARD` was rejected before the engine was reached. Nothing in the branch's original plan covered this; it was found by the session-creation guard's implementer and confirmed by the controller. Widening `validateConfig` is what makes the capability declaration (D196) and the app-mode setting (D195) usable end to end rather than a switch that turns everything off.
Consequences: the predicate is deliberately decoupled from `RULESET_CAPABILITIES` — the validators keep their own mode statement and the capability constant mirrors it, so the two can be cross-checked instead of one silently defining the other. The pair remains asymmetric by design for the other four rulesets: `TUOD_V1` is quick-score only and `SINGLES_V1` / `BOBS27_V1` / `DOUBLES_TRAINING_V1` are `RECREATIONAL + DETAILED_DARTS`, none of which have a visual path. A future ruleset gaining a mode must change both halves and the capability declaration in the same edit, or a parity test fails: `capability-seed-parity.test.ts` covers `RULESET_CAPABILITIES` against seed `0007`, and `capability-validator-parity.test.ts` covers it against every ruleset's `validateConfig` in both directions — a declared pair its validator refuses, and an undeclared pair its validator accepts. (`scripts/check-game-engines.sh` is not a third: it asserts only that a registered engine's ruleset key appears in `RULESET_CAPABILITIES`, and its own header disclaims pair-level parity.)

### D198 — Engines dispatch on the input's shape, not on the session's stored mode
Status: Accepted · Date: 2026-08-09
Supersedes: D189
Decision: `record()`, `wouldComplete()` and `undo()` in `five-oh-one.engine.module.ts` and `score-training.engine.module.ts` branch on what they are handed, never on the constructor's `inputMode` field. A visit total (`number` / `FiveOhOneVisitInput`) takes the quick-score path; a `DartObservation` takes the dart path, discriminated by `hitZoneKey`. `undo()` branches on the last turn's shape (`darts.length > 0`), which is the shape `record()` actually wrote. `inputMode` survives on the constructor for persistence and capability code but governs no engine behaviour. D189's capture-depth model is unchanged — only the mechanism that selects it.
Reason: With dispatch keyed on the field, a QUICK_SCORE-tagged engine handed a `DartObservation` called `classify(undefined, undefined)`, which returns `{zoneKey: "INNER_SINGLE"}` with no target and no score and throws nothing — a silently corrupt dart row. Two reachable paths produced that divergence: setup pages that hardcoded the mode pair, and `playAgain()` rebuilding a replay engine with the factory default. Input shape is the one authority that cannot disagree with the input.
Consequences: The two input paths coexist inside one session, so a player may enter a visit on the keypad and the next on the board. `recordVisitTotal` therefore refuses a keypad total while a dart visit is open (`completedAt === null`) rather than writing across it — refusing loudly beats writing wrong. The mixed log stays undoable to depth because turn shape is an invariant of the write path: `recordVisitTotal` always writes `darts: []`, `recordDart` always writes `darts.length >= 1`, and rehydration is a plain JSON mirror that round-trips shape faithfully. A future method keyed on `inputMode` would silently disagree with its own `record()` — the field is dead and should be removed under its own decision.

### D203 — The engine's `inputMode` field is removed, not merely unused
Status: Accepted · Date: 2026-08-10
Supersedes: D198
Decision: `EngineInputMode` and every trace of it are gone: the third constructor parameter on `FiveOhOneEngine` and `ScoreTrainingEngine`, the third parameter on `GameEngineFactory.create` and both factories, `engineInputMode()` in `session-mode-resolution.ts`, and the `EngineInputMode` type itself. `create(config, prior?)` is the whole contract. D198's shape-dispatch rule is unchanged and is now structural rather than conventional — there is no mode on an engine for a future method to disagree with.
Reason: D198 left the field on the constructor for persistence and capability code and recorded that it "is dead and should be removed under its own decision". It governed nothing, and `astro check` reported it as unused on every run, so the branch shipped two permanent warnings that trained everyone to read a non-empty diagnostic list as clean. Removing the parameter without removing its call sites is what actually broke the build (`ts(2554)`, expected 1-2 arguments but got 3), which is the failure mode of a half-dead field: it stays cheap to keep and expensive to touch.
Consequences: Four tests were DELETED rather than re-pointed — one in `five-oh-one-play.data.test.ts`, three in `score-training-play.data.test.ts` — because their sole assertion was which mode reached `factory.create`, and that argument no longer exists. Per D148 the alternative would have been re-pointing them at a different input to keep them green, which is exactly the failure that rule exists to catch. This drops the only executable guard on D200 at the engine-construction seam; D200's live surface is now the board gate in `BoardInputPanel.astro`, which is `.astro` markup and unit-tested by nothing (D101). The 35 engine tests that passed `"VISUAL_BOARD"` as a third argument kept their bodies and assertions — only the now-nonexistent argument was dropped — and two `undo()` describe titles naming `inputMode` were re-pointed at the same guarantee they always tested, the fact log's shape.

# Phase 6 ships routine statistics: routine and step identity read from the snapshot, a route-fixed routine context, run- and step-level sections, training-step replay, and one cache scope key

## Context and Problem Statement
keying routines and steps off the snapshot (decisions 1–2) is the Template → Snapshot rule applied to statistics — a completed run must not depend on a mutable routine, so neither may its statistics, and a fingerprint is the only index that cannot silently blend two versions of "step 3". Fixing the context in the route and threading one predicate through the existing scope builders (decisions 4–5), instead of editing each game handler, lets every phase 1–4 section serve a GAME step unchanged while the client has no way to widen the scope. A second registry (decision 6) keeps the game registry's `SectionId` and `mergeMetrics` exhaustive, so neither can be handed a routine section by mistake. One metric spec feeding the fold, the chunk merge, the presenters and the summary modal (decisions 7, 11) is what keeps four views of one session from disagreeing, and folding on the server through the phase 5 helpers (decision 8) reuses a bounded, tested path rather than a second one. Whole seconds and a shared routine `versionKey` (decisions 6, 12) keep the phase 1 promise that closed buckets re-aggregate exactly and stale only when the population changes.

## Decision Outcome
Chosen option: "thirteen decisions for the phase 6 build (`docs/superpowers/plans/2026-09-26-statistics-phase-6b-routine-statistics.md`; its database half, migration `0045`, shipped as phase 6a), recorded as built — where review changed the plan's contract, the built form is the one stated:
1. Routine identity is the snapshot's `routineTemplateId`, read from `activity_configurations`, never a template FK, so a deleted routine keeps its statistics. A snapshot written before D321 added that field keys as `name-<md5(routineName)>`, so one legacy name is one routine; the UUID and `name-` forms cannot collide. The display name is the latest run's `routineName`, so a renamed routine keeps its history.
2. Step identity is index plus fingerprint: `step_key = <sequenceNumber>-<md5>`, the md5 of the step's snapshot element without `sequenceNumber` (`jsonb` text output is canonical, so equal steps hash equally). The element is found by `sequenceNumber`, never array position. Any change to a step's exercise, ruleset, duration or configuration starts a new key; earlier keys stay listed as earlier versions of that index. This is stricter than `configSensitive`: a key never mixes configurations, so no step section needs `configGroupKey`.
3. Two views, no widening of `v_stats_session_facts`, which stays game-only: `v_stats_routine_run_facts` and `v_stats_routine_step_facts` (`0045`). A GAME step is in both grains; that is not a second derivation of one fact.
4. `context = routine` is fixed by the route. Every routine query schema is `.strict()`: the two section routes accept `from`/`to`/`tz`/`bucket`/`status` only (`RoutineStatsQuery`), the step session list `from`/`to`/`status`/`limit`/`cursor` (`RoutineSessionsQuery`), the list and the header nothing (`RoutineNoQuery`); anything else is `VALIDATION_FAILED`. A GAME step's section runs the game dispatch with `context: "routine"` and `routineStep: { routineKey, stepKey }` set server-side.
5. One scope predicate: `DartScope`/`SessionScope` gain `routineStep?`, and `dartScopeWhere`/`sessionScopeWhere` add `session_id IN (SELECT session_id FROM v_stats_routine_step_facts WHERE player_id = $p AND routine_key = $r AND step_key = $s)`. Built wider than the plan named: `findBucketedSessionAggregates`, the only phase 1 reader that builds its own `WHERE`, takes the same condition, so a GAME step's `volume`, `completion` and `session-result` are step-scoped too; the game session list and game `dataVersion` readers stay untouched. A GAME step lists exactly `sectionsForGame(gameTypeKey)`; a section outside it is `NOT_FOUND`.
6. A second registry, `ROUTINE_SECTIONS`, of `RoutineSectionMeta` (`SectionMeta`'s fields with `id: RoutineSectionId`, `requires: []` and `surface: "routine" | "step"`); `SectionId` stays game-only, and responses are typed `RoutineSeries<M>`. `routine-volume` (sql, completed runs): `runs`, `durationSeconds`, `minDurationSeconds`, `maxDurationSeconds`, `darts`. `routine-completion` (sql, `includesAbandoned`): `completed`, `abandoned`, `neverStarted`, `stepsCompletedAtAbandon` (started abandons only). `step-volume` (sql): `sessions`, `durationSeconds`, `darts`. `step-result` (server): decision 7. All four are bucketable; runs bucket by the activity's `completed_at`, step sections by the session's; a run with zero step sessions is "never started". Built narrower than the plan's table: `step-volume` serves non-game steps only, because a GAME step's own `volume` already covers it. Durations go on the wire in whole seconds, not the plan's minutes: a minutes float does not re-add exactly across chunks. `sectionsForStep` takes `{ exerciseTypeKey, gameTypeKey }` and no input mode; Warm-Up, which throws no darts, is told by its exercise type and gets `step-volume` only.
7. Per-kind step metrics have one definition, `STEP_METRIC_SPECS: Record<DartExerciseKind, StepMetricSpec>` — metric keys, merge (`sum`/`max`), headline and direction, rate pairs — for Switching, Double Pattern, Target Scoring, Switching Target Scoring, Score Threshold, Bullseye Checkout and Bull Up (`10-Statistics/01-Section-Catalog.md` §3.1). `stepMetrics(kind, state, facts)` reads engine state as `routine-summary.module.ts` did, and the `summarise*` functions now run on it under their unedited tests, so the summary modal and the statistics page cannot disagree. Per bucket `step-result` returns `{ metrics, headlineMin, headlineMax, sessions, skippedSessions }`; chunks merge through `mergeStepResult` (metrics by spec, extremes by `min`/`max` with `null` as identity, counts summed), which lives in the pure `step-metrics.module.ts` beside no engine import, so the client cache can use it.
8. The `step-result` fold runs on the server. `findStepFoldRows` reads `v_game_replay` joined to the step's sessions, each row tagged with its session's bucket as `findX01FoldRows` does. Per session the fold rebuilds facts through `stageOrder`, `rowsToTurns` and `replayFacts` — moved from `lib/stats/replay-fold.ts` to `modules/stats/replay.module.ts`, with its tests moved unchanged — then calls `getDartExerciseEngineFactory(exerciseRulesetVersionKey).create(configuration, facts).state()` over the session's own snapshot, then `stepMetrics`. It is bounded by `MAX_FOLD_DARTS` over the step's scoped `dart_count` and fetched in chunk windows. A session with no registered engine, an engine that throws, or a state lacking the kind's fields is skipped into `skippedSessions`, never guessed.
9. `GET /api/statistics/routines` returns `{ items: TrainedRoutine[] }` (`routineKey`, `routineTemplateId | null`, latest `routineName`, `runCount`, `completedRunCount`, `lastRunAt`), `lastRunAt DESC`, unpaginated. `GET /api/statistics/routines/:routineKey` returns the header with `dataVersion` and `RoutineStepDescriptor[]`, ordered by `sequenceNumber` then `lastSeenAt DESC`; a descriptor's `durationSeconds` is the step's configured length from the snapshot, not elapsed time. `current`, as built: the key is the latest seen at its `sequenceNumber` **and** that index is within the latest run's `step_count`. The plan's "appears in the latest run's snapshot" cannot be read — no view exposes the latest snapshot's step keys, and a latest run stopped early or never started would misread it — and this phase allowed no migration. A malformed `routineKey` is `VALIDATION_FAILED` before any read; an unknown or unowned one is `NOT_FOUND`. The Routines tab stops calling `GET /api/routines`, which lists routines that exist today; statistics need routines that were trained.
10. `GET .../routines/:routineKey/steps/:stepKey/sessions` follows phase 1's session list — cursor, `(completed_at DESC, session_id DESC)`, `status` defaulting to all three — over `v_stats_routine_step_facts`. Each row links to its replay, except a Warm-Up step's.
11. Replay covers training step sessions. The gate is the caller's `v_stats_session_facts` row, or else its `v_stats_routine_step_facts` row with a non-null `input_mode_key`; Warm-Up has no capture pair and stays `NOT_FOUND`. `ReplayHeader` gains `exerciseTypeKey`, `exerciseRulesetVersionKey`, `routineKey` and `stepKey`, left-joined from `v_stats_routine_step_facts`; a standalone game has no step row, so its `exerciseTypeKey` is `GAME` and the other three `null`. `gameTypeKey` becomes nullable, and so — beyond the plan's "phase 5 fields unchanged" — does `rulesetVersionKey`: `chk_exercise_sessions_game_pair` (`0029`) nulls the ruleset whenever the game type is null. The client fold picks `getEngineFactory` when `gameTypeKey` is set, else `getDartExerciseEngineFactory`. `ReplaySkipReason` gains `NO_EXERCISE_ENGINE`; for an exercise session a `null` or non-object configuration is `NO_SNAPSHOT` and any `create` throw — the engine's own configuration decode included — is `ENGINE_THREW`. `STEP_REPLAY_PRESENTERS`, one per dart exercise kind built from decision 7's spec, shows each turn's running headline and darts and the session's final metrics.
12. Cache keys take a scope, not a game: `game:<gameTypeKey>`, `routine:<routineKey>`, `routine:<routineKey>:step:<stepKey>`. The dataVersion for both routine scopes is base64url of `v1:<runCount>:<max activity completed_at epoch ms>` over the routine's terminal runs, through the shared codec. Built beyond the plan: the cache scope is `{ key, gameTypeKey, exerciseKind?, versionKey? }`; the routine and every step scope share `versionKey = routine:<routineKey>`, so one `meta` entry stales both, and `noteDataVersion` records the header's fresh token (the header is never cached) before any section read, so a new run stales the cached open buckets of the routine and of every step before any of them is served. A `step-result` chunk merges with `mergeStepResult` under its `exerciseKind`'s spec; `mergeMetrics` stays game-only. `STATS_SCHEMA_VERSION` 2 → 3 wipes every store, `replayPages` included, which also covers decision 11's header change.
13. Scope out: dart-level sections for non-game steps (heat map, per-target accuracy), which need a non-game dart fact view, additive later; adaptive-training and cross-routine comparisons; a run list or per-run page (a run is reached through its step sessions' replays); merging step keys across edits (an owner-chosen "same step" link would be a new decision); and the `supersededBy` header field, which lands with corrections.".

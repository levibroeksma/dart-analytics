### D188 — Dart coordinates ship as regulation millimetres with a pair-or-neither constraint
Status: Accepted · Date: 2026-08-05
Decision: `darts.location_x` / `darts.location_y` ship as `NUMERIC(6, 2)` millimetres, origin at the bull centre, y increasing downward to match `dartboard.svg` (migration `0017`). Both columns are nullable, but never independently: `chk_dart_location_pair` rejects one present without the other. `v_dart_locations` (migration `0018`) exposes them plus derived `radius_mm` / `angle_degrees`; miss margin needs a zone centroid, which stays out of SQL entirely and is computed in the application read layer (`app/src/lib/game/board/miss-margin.module.ts`) instead.
Reason: A landing point is one fact, not two independently-optional columns — the CHECK constraint makes "half a coordinate" unrepresentable rather than a client-side convention. This is the shipped shape that replaces the deferral recorded in `06-Spec/04-Runtime-Layer.md` ("`location_x`/`location_y` board coordinates are deferred"), now that the visual board UI can capture them.
Consequences: Migration `0017` also adds the two `player_settings` foreign keys (`fk_player_settings_capture_mode`, `fk_player_settings_input_mode`) that `06-Spec/03-Player-Layer.md` specified but `0003` never created — bundled because both were reviewed together and neither is separable from the other in that migration. No capability table ships alongside this pair; it is deferred to a later plan.

### D192 — SQL that a migration can only fail on gets a real-database run, not a review
Status: Accepted · Date: 2026-08-08
Decision: `v_dart_locations`' angle expression casts to `NUMERIC` before `MOD()` (`MOD(DEGREES(ATAN2(x, -y))::NUMERIC + 360, 360)`), and `app/tests/db/migration-numeric-typing.test.ts` fails any migration whose `MOD()` argument reaches a double-precision function without an intervening `::NUMERIC`. Both derived columns are therefore `NUMERIC`, which Drizzle/node-postgres surface as strings.
Reason: migration `0018` shipped with `MOD(DEGREES(...) + 360, 360)` and could never have applied — PostgreSQL has no `mod(double precision, integer)`, and the double→numeric cast is assignment-only so it is not considered during function resolution. Nothing caught it: `tsc` and the whole Vitest suite are blind to SQL, the structural gates lint file shape rather than semantics, and the plan's own verification was deferred to an operator checklist. The bug was found only by running the chain against a throwaway PostgreSQL 16 cluster.
Consequences: `0018` is corrected in place rather than superseded — it had never applied to any database, so no environment carries the broken definition and the "never modify applied migrations" invariant (`0001`–`0016`) is untouched. Operator checklist steps 1 and 3–5 are now verified against a real cluster and marked as such; only the Neon-specific re-run remains. The read layer must parse `location_x`, `location_y`, `radius_mm` and `angle_degrees` from strings before handing them to `missMargin`, which takes numbers. A migration that only a live database can reject should be run against one before the branch claims verification.

### D193 — Live-database verification is a committed script, not checklist prose
Status: Accepted · Date: 2026-08-08
Decision: behaviour only a real database can demonstrate — a CHECK constraint firing, a view expression resolving, a derived column reading correctly — is asserted by a script under `database/verification/`, named for the migration it covers (`0018_visual_board_checks.sql`). Each script builds its own fixture inside one transaction, resolves every seeded lookup row by `implementation_key` rather than by hardcoded id, emits one PASS/FAIL row per check with the observed value in a `detail` column, and ends in `ROLLBACK`. Operator handoffs invoke the script instead of restating the SQL.
Reason: the original checklist told the operator to find "a real `turn_id` from a test session" and hand-type inserts against it. That is the shape of a step that gets skipped, and D192's `0018` defect is what skipping it costs. A script removes both the setup burden and the transcription risk, and it is re-runnable — the same checks that passed on the local PostgreSQL 16 cluster can be pointed at Neon, or at any future environment, without rewriting anything. Ending in `ROLLBACK` is what makes it safe to run against a seeded dev database rather than a scratch one.
Consequences: a join-driven check reports a vacuous pass when its source view is empty, so each script must separately assert that the expected number of checks ran — `0018_visual_board_checks.sql` does. Scripts must be proved non-vacuous before they are trusted: this one was, by swapping the view's angle expression to `ATAN2(y, x)` and confirming 4 of 11 checks went red. These scripts are not part of `npm test` — they need a live `DATABASE_URL` and are run deliberately, per environment. `database/CLAUDE.md`'s validation checklist carries the rule.

### D212 — Darts equipment lives on `players`, not `player_settings` or a new table
Status: Accepted · Date: 2026-08-15
Decision: `darts_description` (nullable `TEXT`) and `darts_weight_grams` (nullable `SMALLINT`, 1–100) are added to `players` (migration `0022`), read through a new `v_player_profile` view alongside `display_name`, and written by `PATCH /api/players/me` — replacing all three fields together, no partial update, the same convention `PATCH /api/players/me/settings` established.
Reason: two alternatives were weighed and rejected during design. `player_settings` was rejected because its semantics are gameplay-mode defaults copied onto a session at start — equipment is not a game-start default and copying it onto sessions would misrepresent it as one. A new `player_equipment` table was rejected as premature: the ask is one current dart set, not a collection, and a dedicated table for a single scalar pair is YAGNI until multiple dart sets are actually needed.
Consequences: `03-Player-Layer.md`'s "rename endpoint deferred post-v1" note is resolved — `GET`/`PATCH /api/players/me` is that endpoint, now also carrying darts equipment. `v_player_profile` is a plain projection over `players` with no joins, since neither new column is FK-backed. If multiple dart sets are ever needed, this shape is superseded, not extended in place.

### D222 — The dart analytics views are scoped to the session's owning participant
Status: Accepted · Date: 2026-08-21
Decision: Migration `0023` adds `JOIN participants p ON p.id = t.participant_id` and `AND p.player_id = es.player_id` to both `v_dart_analytics` and `v_dart_locations`. `v_game_replay` is deliberately left unfiltered.
Reason: Guest participants (D220/D221) throw into the same `turns`/`darts` tables as the owning player, and both views project `es.player_id` with no participant filter — so a guest's darts would have entered the owner's accuracy statistics the moment a second seat could exist. Multiplayer is what makes the omission wrong, which is why it was fixed as part of that work rather than logged as a finding. `v_game_replay` is the opposite case: it projects `p.display_name` and exists to replay a session as it was played, every participant included.
Consequences: Behaviour-preserving for every existing session — a single-participant session has exactly one participant, the `PLAYER` whose `player_id` equals `es.player_id`, so no existing row is dropped. The play-time stat row on the 501 screen is deliberately NOT scoped: on a pass-and-play device that row belongs to whoever is throwing, and how it should be presented for several seats is the drawing spec's question. The results snapshot IS scoped, in the client, by filtering the fact log to the one `PLAYER` seat.

### D248 — `npm run db:seed` runs the full seed list twice, not once
Status: Accepted · Date: 2026-08-29
Decision: `app/scripts/seed.ts`'s `run()` executes every file returned by `seedFiles()` twice in the same invocation (`buildExecutionPlan`), instead of once.
Reason: `seeds/0007_ruleset_version_capabilities.sql` is a running ledger — every new ruleset version's capability rows are appended to it, joined against `ruleset_versions` by `implementation_key` — but a new ruleset's own `ruleset_versions` row is created by whichever seed introduces it, which sorts after `0007` whenever its number is higher (e.g. `0013`). Production hit this directly: seeding #204's `SINGLES_V2` ruleset (`0013`) after `0007` was extended with its two capability rows meant the first pass's join matched nothing when `0007` ran, `ON CONFLICT DO NOTHING` gave no error, and `SINGLES_V2` sessions failed on `fk_sessions_capability` (migration `0020`) until a second manual `db:seed` run resolved it. Two alternatives were rejected: renumbering `0007` to sort last doesn't hold, since a ledger appended to indefinitely will always eventually receive an entry whose dependency is numbered higher than whatever "last" is at the time; a dependency graph between seed files was rejected as more machinery than a single ordering bug — that has recurred exactly once in thirteen files — justifies.
Consequences: Every seed file must stay `ON CONFLICT DO NOTHING` (already required) so a second pass is a safe no-op rather than a duplicate insert or error; this was already true of every existing seed. Production seeding cost roughly doubles, which is negligible at this table size. `app/tests/scripts/seed.test.ts` asserts `buildExecutionPlan` doubles the file list; it does not exercise the join failure itself, since that requires a live database (see D193).

### D257 — Split `05-Views.md` into a directory; general stat views expose raw facts only
Status: Accepted · Date: 2026-09-06
Decision: `05-Views.md` became `05-Views/` (`00-Overview.md` + `01-General-Views.md`, future `02-X01-Views.md` etc.) so per-domain view catalogs don't all pile into one growing file. Migrations `0025`/`0026` add `v_player_visit_facts`/`v_player_leg_facts`, exposing row-level facts only (real dart counts, configured maxes) — no stat-card computation, no application module.
Reason: A single `05-Views.md` growing indefinitely as more analytics views ship was the same problem D184's context-system split solved elsewhere — per-domain catalogs scale better than one file. The two new views' consumption layer (stat-card computation, approximation rules) is deliberately out of scope for this work and is being designed separately by the user. Win-rate was scoped out entirely — it needs session-replay-from-persisted-facts, which doesn't exist for any engine yet; see `docs/superpowers/specs/2026-09-06-general-statistics-views-design.md`.
Consequences: `v_player_leg_facts` narrows its own population (excludes any leg where a turn lacks real dart rows) rather than approximating an unknowable QUICK_SCORE dart count, the same precedent as `v_dart_analytics`'s target/zone filter. No API endpoint, repository, or UI reads either view yet.
Supersedes: none.

### D263 — Exercise sessions carry an exercise-type discriminator, and exercise rulesets are a separate table
Status: Accepted · Date: 2026-09-10
Decision: Migrations `0027`–`0031` add an `exercise_types` catalog (UUID primary key) and an `exercise_ruleset_versions` table, give `exercise_templates` and `exercise_sessions` an `exercise_type_id`, relax `game_type_id`/`ruleset_version_id`/`capture_mode_id`/`input_mode_id` on `exercise_sessions` to nullable under two independent CHECK constraints, add `routine_steps.configuration` (JSONB), and add an `activity_configurations` snapshot table. `ruleset_versions` and `configuration_templates` are left unchanged.
Reason: Every game-bound column was `NOT NULL`, which forced a game abstraction onto a non-game exercise — exactly what `docs/architecture/09-Training/01-Routines.md` §12 forbids. Three alternatives were weighed and rejected. A discriminator on `ruleset_versions` was rejected because a game-backed exercise (§11) holds an exercise ruleset and a game ruleset simultaneously and one `ruleset_version_id` column cannot carry both. A SMALLINT primary key for `exercise_types` was rejected because §26 makes each new exercise type ship with its own ruleset, engine and configuration schema — a growing catalog like `game_types`, not a fixed structural enum like `stage_types`. Putting the warm-up's phase list in `configuration_templates` was rejected because that table is game-keyed and models the §19 named-preset concept; §3.5's per-routine exercise configuration belongs on the step.
Consequences: The two CHECK constraints are deliberately independent — `SWITCHING` (§17) takes dart observations with no game engine, so a capture pair must be settable without a game pair — and neither names a specific exercise type, so no new exercise type requires a constraint change. Migration `0020`'s composite `fk_sessions_capability` is left in place: it is `MATCH SIMPLE`, so a fully-NULL warm-up row satisfies it trivially, at the cost of the capability guarantee not extending to non-game exercises that take dart input. `exercise_sessions.exercise_type_id` needs the `db:migrate` → `db:seed` → `db:migrate` apply order that `0019`/`0020` established, because its backfill is seed data. Adaptive resolution (§21) has a place to land with no further schema change: it rewrites the resolved step list before it is snapshotted into `activity_configurations`.
Supersedes: none.

### D266 — `exercise_templates.exercise_type_id` follows the same nullable → backfill → NOT NULL shape as `exercise_sessions`
Status: Accepted · Date: 2026-09-10
Decision: Migration `0028` adds `exercise_templates.exercise_type_id` as nullable, not `NOT NULL`. Seed `0014_exercise_types.sql` backfills existing rows to GAME (in addition to its existing `exercise_sessions` backfill). A new migration `0032` promotes the column to `NOT NULL` after the seed runs.
Reason: `0028`'s original comment claimed `exercise_templates` was "confirmed empty in production," which was false — `seeds/0002_default_templates.sql` already ships four rows (501 Match, Ten Up One Down, Singles Accuracy, Score Training Block) that predate the column. Adding it `NOT NULL` directly fails with `23502` against any database that has run seed `0002`, which is every real environment. `0028` was editable in place rather than patched forward because it had never once committed against a real database — every attempt errored and rolled back, so no deployed schema ever reflected its old text; `0031`'s NOT NULL for `exercise_sessions` proved the same seed-backfill shape works for this exact discriminator.
Consequences: The apply order for the full chain is now `db:migrate` (through `0031`) → `db:seed` → `db:migrate` (`0032`), run alongside `0031` in that final pass. `exercise_templates.exercise_type_id` is enforced NOT NULL from `0032` onward, same as `exercise_sessions.exercise_type_id` from `0031`.
Supersedes: D263 (corrects `0028`'s emptiness assumption and adds `0032`; the rest of D263's decision stands unchanged).

### D284 — Training gameplay counts towards career statistics, so the read model LEFT JOINs every lookup a non-game session leaves NULL
Status: Accepted · Date: 2026-09-16
Decision: Training exercise sessions are part of career statistics, session history and the active-session read — not a separate, excluded population. Migration `0033` therefore converts every read-model join onto a lookup that `0028`/`0029` made nullable into a `LEFT JOIN`: `game_types` in `v_active_sessions`, `v_session_overview`, `v_dart_analytics`, `v_dart_locations`, `v_player_visit_facts`, `v_player_leg_facts` and `v_routine_execution`, plus `ruleset_versions`/`capture_modes`/`input_modes` in `v_active_sessions`, `capture_modes` in `v_session_overview` and `input_modes` in `v_dart_locations`. The `*_key`/`*_name` columns those joins feed are nullable from `0033` onward, and that nullability is carried through the API read layer (`SessionActive`, `PlayerSessionSummaryRow`, `PlayerVisitFactRow`, `PlayerLegFactRow`, `PlayStoreContext`'s `setSessionModes`). `v_configuration_presets` and `v_double_out_checkout_darts` keep their INNER joins.
Reason: issue #343. `0029` relaxed `exercise_sessions.game_type_id` to nullable but generalised no view with it, so the training gameplay D277 and D281 had just made persistent was written to `turns`/`darts` and then readable by nothing — invisible to `totalDartsThrown`, the score bands, the averages, `totalPlayTimeSeconds`, session history and `GET /api/sessions/active`. The views' own comments already claimed inclusion ("every game type and capture mode"), so the gap read as working code. The alternative — documenting the exclusion instead — was rejected by the repo owner: a darts session the player actually threw is career history regardless of whether a game engine scored it.
Consequences: An INNER JOIN onto a nullable FK is now a recognised read-model defect, recorded in `05-Views/00-Overview.md` under View Column Naming. `favoriteGameTypeKey` skips NULL-keyed rows — a session with no game cannot be a favourite game — while `totalGamesPlayed`/`totalPlayTimeSeconds` count them. `gamesIndex` drops an active session with no ruleset version, which gates no card. `setSessionModes` takes `SessionModePair` (both keys nullable) rather than `ModePair`; the store's own mode fields were already nullable. The two excluded views are excluded for a stated reason, not by omission: `configuration_templates.game_type_id` is still NOT NULL, and `v_double_out_checkout_darts` filters to 501 `VISUAL_BOARD` in its own WHERE clause, which no non-game session can satisfy. `0033` was not applied to any database by the authoring session — no dev branch credentials were reachable — so `db:migrate`/`db:introspect` have not run against it and `app/src/db/schema.ts`'s view bodies were hand-edited to match, the D193 precedent.
Supersedes: none.

### D288 — Production migrations are applied by the deploy pipeline, behind a rehearsal on a Neon branch cut from production
Status: Accepted · Date: 2026-09-17
Decision: `.github/workflows/deploy.yml` runs `quality → rehearse → migrate → deploy` inside the existing `deploy-production` concurrency group. `rehearse` (`.github/workflows/db-rehearsal.yml`, also triggered on any PR touching `database/migrations/**`, `database/seeds/**`, `database/verification/**`, the seed/verify runners or `app/package.json`) creates a throwaway Neon branch from `main`, applies migrations and seeds, confirms nothing is left pending, and deletes the branch in an `always()` step. It deliberately does not run `db:verify`. `migrate` then applies the same chain to production and re-runs `db:status` to prove nothing is left pending. Four `:ci` script variants (`db:status:ci`, `db:migrate:ci`, `db:seed:ci`, `db:verify:ci`) read `DATABASE_URL` from the environment rather than an `.env` file and pass `--no-dump-schema`, since CI has no `pg_dump`; the `:prod` variants are untouched. Two secrets are required — `DATABASE_URL` on the `production` environment and a repository-level `NEON_API_KEY`; the Neon project id is read from committed `app/.neon` and is not a secret.
Reason: issue #293. `deploy.yml` shipped the Worker on every merge and never touched the database, so a merged migration produced a Worker expecting a schema production did not have — measured once already, when `0024`–`0026` sat unapplied and `GET /api/statistics/overview` returned `INTERNAL_ERROR` for `relation "v_..." does not exist`. The manual step (`npm run env:prod` then `db:migrate:prod`) was enforced by nothing, and CI was green either way. Automating the apply without a rehearsal would only have made that failure faster, which is why the rehearsal is the gate rather than an advisory job.
Consequences: the ephemeral branch is a real rehearsal against production's data shape, not a simulation against an empty container — a migration that fails only on existing rows fails in `rehearse`, before production is touched. It costs one Neon branch and one short-lived compute per deploy, and it needs an API key CI did not previously hold; a failed delete leaves a branch behind and warns rather than failing the run, so a leaked `ci-rehearsal-*` branch is possible and is cheap to remove by hand. Seeds run on every deploy: every seed is `ON CONFLICT DO NOTHING` and the runner applies them twice by design, so this is a no-op once they are in. `db:verify` is excluded from the rehearsal, which the first real run forced and justified: the suite asserts on live data as well as on its own fixtures, so against production's rows it reports data state rather than whether the change applied, and it cannot currently pass at all — six fixtures predate `0031`'s NOT NULL (#383), 53 of 404 sessions are undeclared against the capability table (#384), and `0007`'s VALUES lists are two ruleset versions stale (#304). A gate that cannot pass is not a gate; making it non-blocking instead was rejected for D186's reason, that a permanently-red signal is one nobody reads. It returns to the rehearsal when those three are resolved. The same first run also exposed that seed `0002` had been unappliable since `0032` promoted `exercise_templates.exercise_type_id` to NOT NULL — fixed in this change by joining both of its inserts to the rows they depend on, since NOT NULL is checked before `ON CONFLICT` is consulted and an already-seeded database could not re-run the file either. A mid-way migration failure blocks the Worker deploy and leaves production partly migrated: that is deliberate, since shipping a Worker onto a half-applied schema is the worse of the two, and the rehearsal exists to make it unlikely. Drizzle artifact regeneration (issue #352) is now unblocked but is not part of this change.
Supersedes: none.

### D290 — `schema.ts` is the only committed `drizzle-kit introspect` artifact, and the migration chain is authority over its view bodies
Status: Accepted · Date: 2026-09-17
Decision: `app/src/db/0000_curved_gwen_stacy.sql`, `app/src/db/relations.ts` and `app/src/db/meta/` are deleted and gitignored; `drizzle-kit introspect` still writes them into `out/`, but only `app/src/db/schema.ts` is committed. `app/tests/db/schema-view-drift.test.ts` compares every `pgView(...).as(sql`…`)` body in `schema.ts` to the last `CREATE VIEW` for that view in `database/migrations/`, and asserts the two view sets are identical. The chain is authority: a mismatch is reconciled in `schema.ts`, never in an applied migration. The comparison normalizes case, whitespace, `::type` casts and parentheses, because those are what Postgres rewrites when it echoes a definition back.
Reason: issues #363 and #352. The dump and `meta/` were frozen ~20 migrations behind — no `activity_configurations`, no `exercise_ruleset_versions`, pre-`0013` view text — so two artifacts in the same folder disagreed about what the schema is, and the next introspect would have diffed against a stale snapshot. Nothing imports them: only `schema.ts` is read, by five repositories and the middleware. Regenerating them instead was rejected because it buys a second copy that can go stale again, and D288 makes regeneration a per-deploy possibility rather than a one-time fix. Separately, `schema.ts`'s own view bodies drifted undetected from 2026-08-21 to 2026-09-16 — `vDartAnalytics` and `vDartLocations` carried the pre-`0023` SQL, missing the owner-scoping `0023` was written to add — because no gate compared them to the chain.
Consequences: the generator's output is no longer self-contradictory, and `db:introspect` inside `validate:app` can no longer re-commit a stale sibling. The drift gate is static, so it needs no database and runs in `npm test` and CI — which matters, since no session that has touched these views since `0023` had credentials to run a real introspect. Normalizing parentheses away is the cost: a drift that only regroups an existing expression (`a AND (b OR c)` becoming `(a AND b) OR c`) reads as a match. That was chosen over hand-rewriting five bodies into Postgres's echo form, which no one here can verify without a database. The gate compares text, not semantics — it proves `schema.ts` agrees with the chain, never that either agrees with the live database. `relations.ts` was deleted alongside the other two on the repo owner's instruction; it was equally unreferenced and equally stale.
Supersedes: none.

### D291 — `uq_sessions_single_active` keys on the exercise a session actually ran
Status: Accepted · Date: 2026-09-17
Decision: migration `0034` rewrites `uq_sessions_single_active` to `(player_id, COALESCE(game_type_id, exercise_type_id)) WHERE completed_at IS NULL`, and closes pre-existing duplicates (newest `started_at` per key survives; the rest become ABANDONED with `completed_at = now()`) so the index can be created. `database/verification/0034_single_active_session_checks.sql` proves it against a live database. The backfill is not reversed by `migrate:down`.
Reason: `0029` made `game_type_id` nullable so a training step could run without a game. Postgres treats every NULL as distinct for uniqueness, so from `0029` onward the index — named and documented as the single-active-session guard — constrained nothing for WARM_UP, SWITCHING or DOUBLE_PATTERN sessions (issue #310). A duplicated or retried step start inserted a second open row for the same player with no DB-level signal. `COALESCE` was chosen over `NULLS NOT DISTINCT` because the latter collapses all non-game sessions into one key, which would forbid a player from having, say, an open Switching and an open Warm-Up session; the expression keeps the rule "one open session per kind of thing being done".
Consequences: the index now bites on a path that previously could not fail, so `startTrainingStep` must handle `23505` for non-game steps as well as game steps — done in the same change (D292). An expression index cannot be declared as a plain Drizzle column list; `app/src/db/schema.ts` carries the `COALESCE` as raw `sql`, which `drizzle-kit introspect` will render its own way on the next run (issues #352/#363 track that drift). Activity-level uniqueness is deliberately not addressed here: `activities` rows created by the game path are never closed, so no partial unique index over `activities` can be written until that lifecycle gap is fixed.

### D295 — An exercise template pins the exercise ruleset version it was written against
Status: Accepted · Date: 2026-09-17
Decision: migration `0035` adds `exercise_templates.exercise_ruleset_version_id` (nullable) and a *composite* foreign key on `(exercise_type_id, exercise_ruleset_version_id)` referencing `exercise_ruleset_versions (exercise_type_id, id)`, backed by a new `uq_exercise_ruleset_versions_type_id`. Seed `0019` backfills the three non-game system templates to their own v1 ruleset; the GAME template stays NULL. `findRoutineTemplateSteps` joins the version on that column instead of on `exercise_type_id`. `database/verification/0035_exercise_template_ruleset_version_checks.sql` proves it against a live database.
Reason: issue #338. The join resolved a step's ruleset version by exercise type with no version predicate, which is unambiguous only because exactly one version exists per type today (`WARM_UP_V1`, `SWITCHING_V1`, `DOUBLE_PATTERN_V1`). The first second version of any type would fan the `leftJoin` out: every step row of that type duplicates and the session pins to whichever version row order happens to surface — a replay-integrity break that surfaces as duplicated steps in a routine, not as an error. The column went on `exercise_templates` rather than `routine_steps` because `default_configuration` and the ruleset version defining its shape are both the template's; a per-step override would let one step's configuration diverge from its own template's. The foreign key is composite rather than simple so that a Switching template pinned to `WARM_UP_V1` is unrepresentable — a simple key would accept it, the join would return a row, and the step would validate against the wrong ruleset with nothing reporting it.
Consequences: adding a second version of an exercise type is now a deliberate act — an existing template keeps pointing at the version it was written for until someone repoints it. The column is nullable and stays nullable: a GAME template pins a game ruleset version on its session instead, and MATCH SIMPLE skips FK validation when either column of the pair is NULL. "A non-game template must pin a version" is therefore not a schema constraint; it is asserted in `startTraining` (D296), which refuses to open an activity whose step resolves no validator. A CHECK pairing `game_type_id` against the new column was rejected because it would hardcode game-backed ⇔ no-exercise-ruleset into the schema and would add a third "migrate stops until the seed runs" trap of the `0020`/`0007` kind. Neither the migration nor the seed was executed here — no `DATABASE_URL` in this environment (D193) — so `schema.ts` was hand-edited to match, as migration `0034` was.
Supersedes: none.

### D305 — Custom-routine duration floor is a deferred constraint trigger scoped to user-owned routines
Status: Accepted · Date: 2026-09-17
Decision: The planned 30-60 minute duration bound for player-authored routines (`docs/superpowers/specs/2026-09-17-configurable-training-routines-roadmap-design.md` §3.2-3.3) is enforced by a deferred constraint trigger on `routine_steps`, evaluated at transaction commit, checking the step-duration sum only when the parent `routine_templates.is_system_template = FALSE`. Consequences: unbuilt — no migration exists yet; this records the design so Phase 1's implementation doesn't relitigate it. The existing ≤60 minute ceiling (`09-training-routines.md` §7) is unchanged and continues to apply to every routine, system or user.
Supersedes: none.

### D333 — Shared `dev` drift is caught by comparing applied migrations and live views to the chain, not by trusting `dbmate status`
Status: Accepted · Date: 2026-09-19
Decision: `app/scripts/check-migration-drift.ts` (`npm run db:drift`) compares `schema_migrations` to `database/migrations/` in both directions, and the live `v_*` views to the set the chain's `migrate:up` regions leave behind, replayed in migration order. It runs inside `validate:app` between `db:migrate` and `db:introspect`. Neon `dev` was reconciled by rolling migration `0038` back — the mechanism that applied it, run in reverse — not by adding a migration.
Reason: issue #503. `dev` is one database shared by every task branch (D24), while migrations live per git branch, so migrating on a branch applies that branch's schema to everyone and switching away does not undo it. On 2026-09-19 `dev` carried `0038` from the never-pushed branch `fix/x01-checkout-percentage` — `v_double_out_checkout_darts` dropped, `v_x01_checkout_darts` created — and `npm run db:status` still reported `Applied: 37 / Pending: 0`. That is not a dbmate bug: dbmate enumerates the migration *files* and prints each one's applied flag, so a `schema_migrations` row with no file produces no line at all. The consequence is not cosmetic. `validate:app` runs `db:introspect` one step later, which regenerates `app/src/db/schema.ts` from whatever `dev` happens to be; the regenerated file dropped `vDoubleOutCheckoutDarts`, which `app/src/repositories/statistics.repository.ts:103` reads, and the suite still passed 4538/4538 because it mocks the query builder. The gate is positioned before introspect for exactly that reason — after it, the wrong schema is already in the tree and only a reverted file separates it from a commit. The view comparison is carried alongside the version comparison because DDL run by hand leaves no `schema_migrations` row, so the version check alone cannot see it; #503's own hypothesis was that this had happened, and nothing in the repo could have confirmed or refuted it.
Consequences: `db:drift` requires `DATABASE_URL`, so it is a local gate — CI's `quality` job has no database and does not run it; the Neon-branch rehearsal (D288) covers the chain's applicability to production instead. A task branch that adds a migration now fails `db:drift` for every *other* branch until it lands or is rolled back, which is the signal, not a defect — but it makes an unlanded migration's cost visible where it was previously free. Rolling `0038` back means `fix/x01-checkout-percentage` must re-run `npm run db:migrate` when that work resumes; its `migrate:down` restores `0036`'s definition byte-identically, so nothing was lost. View *bodies* stay out of scope: `app/tests/db/schema-view-drift.test.ts` compares bodies in `schema.ts` to the migrations (D290), and nothing compares live bodies to either — a view edited in place still passes. Tables, columns, indexes and constraints are equally uncovered and still surface only as an introspect diff. Whether production carries the same drift was not established: `db:status:prod` was refused by this environment, and the inference that it is clean rests only on `0038` never having merged.
Supersedes: none.

### D334 — The duration-bound trigger raises one constraint name regardless of which trigger fired, and the service matches on it literally
Status: Accepted · Date: 2026-09-19
Decision: `fn_routine_templates_duration_bounds()` (migration `0038`) is the single function body behind both `trg_routine_steps_duration_bounds` (on `routine_steps`) and `trg_routine_templates_duration_bounds` (on `routine_templates`); its `RAISE EXCEPTION` always sets `CONSTRAINT = 'trg_routine_templates_duration_bounds'` literally, whichever of the two triggers invoked it. `app/src/services/routine.service.ts`'s `isRoutineDurationViolation` hardcodes that exact string as its `DURATION_BOUND_TRIGGER` constant and matches a caught error's `constraint`/`message` against it alone to map the failure to `VALIDATION_FAILED` — it never checks for `trg_routine_steps_duration_bounds`, and does not need to.
Reason: a per-trigger `CONSTRAINT` name would have made the service check two strings for one logical failure, for no benefit — both triggers enforce the identical 30–60 minute rule through the identical function, so collapsing the raised identity onto one literal name is the simpler contract. Recording it here is what D336 stopped short of: D336 names both trigger objects but never states that only one of the two names is ever actually raised, or that the service's error classification depends on that being true.
Consequences: this is a coupling a future migration can break silently. Renaming either `CREATE CONSTRAINT TRIGGER`, splitting `fn_routine_templates_duration_bounds()` into two functions with their own `RAISE`, or dropping the `CONSTRAINT =` clause would not fail any test that doesn't exercise a live Postgres violation (`isRoutineDurationViolation`'s own unit tests use fixture errors, not a real trigger) and would turn every over/under-duration write into an unhandled `INTERNAL_ERROR` (500) instead of `VALIDATION_FAILED`, with nothing in the ledger to flag it before that migration ships. A future change to this trigger must keep the `CONSTRAINT = 'trg_routine_templates_duration_bounds'` literal, or update `routine.service.ts`'s `DURATION_BOUND_TRIGGER` in the same commit.
Supersedes: none.

### D335 — The duration-bound trigger function picks its row by `TG_OP`, never by `COALESCE(NEW, OLD)`; `0038` corrected in place
Status: Accepted · Date: 2026-09-19
Decision: `fn_routine_templates_duration_bounds()` (migration `0038`) resolves the routine to bound by branching on `TG_OP` and `TG_TABLE_NAME` — `OLD.routine_template_id` on a `routine_steps` DELETE, `NEW.routine_template_id` on INSERT, both parents on an UPDATE that re-parents a step, `NEW.id`/`OLD.id` on `routine_templates` — replacing `COALESCE(NEW.routine_template_id, OLD.routine_template_id)`. `0038` was edited in place rather than corrected by a `0039`: it is committed but applied to no database (D336, D193), and the "never modify applied migrations" invariant covers `0001`–`0037`. `database/verification/0038_custom_routine_checks.sql`'s check 8 (the delete path) now catches `OTHERS`, not only `check_violation`. Both couplings the trigger carries are pinned from TypeScript by the new `app/tests/db/routine-duration-bound-drift.test.ts`: the `30`/`60` literals against `routine-duration.module.ts`'s constants, and the raised `CONSTRAINT` name against `routine.service.ts`'s `DURATION_BOUND_TRIGGER`.
Reason: in a PL/pgSQL row trigger `NEW` is *unassigned* on DELETE — structurally absent, not NULL-valued — so reading it raises `record "new" is not assigned yet` (SQLSTATE 42804) before `COALESCE` can reach its second argument. Every `PUT /api/routines/:id` (`replaceRoutine` deletes the routine's steps inside its transaction) and every `DELETE /api/routines/:id` (cascade to `routine_steps`) would therefore have failed at COMMIT with a 42804 that `isRoutineDurationViolation` does not match — it matches `23514` alone (D334) — rethrowing to a 500 with the routine unchanged. Check 8 exists to prove exactly that delete path and could not report it: a 42804 escaped its `WHEN check_violation` handler and aborted the whole script instead of recording a FAIL. Re-checking both parents on a re-parenting UPDATE closes the same class of hole from the other side: the old parent's total changes too, and nothing else would look at it.
Consequences: D334's Consequences said no test could catch a drift in the raised `CONSTRAINT` literal short of exercising a live Postgres violation; that is now narrower — `routine-duration-bound-drift.test.ts` fails on a rename of the literal or a change to the `30`/`60` bound on either side. It still cannot prove the trigger fires, that `NEW`/`OLD` are read correctly, or that the bound is enforced at all: only `database/verification/0038_custom_routine_checks.sql` run against a live database can, and `0038` is still applied to no database (D193, D336). A future trigger added to this chain inherits the rule this one got wrong — a row trigger that handles more than one `TG_OP` must select `NEW` or `OLD` per operation, never by `COALESCE`.
Supersedes: none.

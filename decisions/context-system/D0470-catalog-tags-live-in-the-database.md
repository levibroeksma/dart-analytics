# Catalog tags live in the database, generated from `docs/game-rules/TAGS.md`

## Context and Problem Statement
hardcoded card tags do not scale and drift from the rules; a database vocabulary lets filters, plans and routine profiles read one source. Docs stay the authority, so the seed is generated rather than hand-written, and the drift gate makes a stale seed a CI failure rather than a silent mismatch. Difficulty varies per template (a 1-dart and a 3-dart preset differ), which the per-type tag cannot express, so it is seeded per template and checked against the docs.

## Decision Outcome
Chosen option: "the tag vocabulary of D461 is stored in migration `0047` tables `tag_axes`, `tag_contexts`, `tags` (unique `uq_tags_axis_sort_order`), the typed link tables `game_type_tags` and `exercise_type_tags`, and `exercise_templates.difficulty_tag_id`; views `v_catalog_tags` (with `axis_rank`) and `v_exercise_template_catalog` (plus `exercise_type_name`, `game_type_name`, `difficulty_level`, `exercise_type_description`, `game_type_description`) feed `GET /api/catalog-tags` and the Games screen and exercise picker cards. Rows come from `database/seeds/0042_catalog_tags.sql`, GENERATED by `app/scripts/generate-tag-seed.ts` from `TAGS.md` and the `## Tags` sections (upsert lookups, delete and refill links, explicit `now()` timestamps). `scripts/check-tag-seeds.sh` fails CI when the committed seed drifts from the docs. Per-template difficulty is seeded by hand in `0043_exercise_template_difficulty.sql` and proven against the rules docs by a parity integration test. Spec: `docs/superpowers/specs/2026-10-18-catalog-cards-and-tags-design.md`.".

### Consequences
tag ids are positional in `TAGS.md` order, so `TAGS.md` is append-only: a new value or axis is appended, while reordering or removing one needs a migration (`uq_tags_axis_sort_order` is non-deferrable, so an in-place renumbering cannot pass). `tag_axes` carries no cardinality; the rules (one primary Skill, Pressure NONE exclusive) stay in `TAGS.md` and `check-game-rules.sh`. Scope is limited to types with a playable card or system template; no coming-soon rows. A game whose rules file has no `### Routine step` block still gets a `ROUTINE_STEP` copy of its tags (minus Family) in `game_type_tags`, which nothing reads yet; a future routine-step filter must decide routine eligibility from the rules file's entry points, not from the presence of `ROUTINE_STEP` rows. Next step: a `v_game_catalog` view replacing `GAME_CARDS` except `href`, so `is_published = false` rows can drive coming-soon cards and filters read the same source as the card list. Deferred as in D461: template-level overrides beyond difficulty, derived routine profiles, filters in the routine builder, tags on routines and trivia.
